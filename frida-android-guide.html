Frida Android 源码与工作原理导读

从敲下 frida -U -N com.example.demo -l hook.js 开始，沿着电脑命令进程 → Android 服务端进程 → 目标 App 进程三条 PID 边界，拆解 Frida 的源码组织、静态链接与动态注入产物、跨机通信协议，以及 Java Bridge 如何在运行时接管 ART 方法。

01 / Mental Model

一分钟看懂全局：先按 PID 划清边界

初读 Frida 源码最容易迷失在十几个子仓库和产物名里：frida-core、frida-gum、GumJS、_frida.pyd、frida-server、agent.so 到底谁调用谁？最不容易乱的方法不是背仓库，而是先看它们各自活在哪个进程（PID）里。

STAGE 01

电脑发令

Python CLI 读取 hook.js，经 _frida.pyd 调入静态链接的电脑端 Core。

STAGE 02

跨机建连

电脑端 Core 复用 ADB 通道建立 D-Bus 连接，向手机上的 frida-server 查询并附加目标 PID。

STAGE 03

注入落点

frida-server 按需将 frida-agent.so 注入目标 App 进程，随后把 JS 源码送入 App。

STAGE 04

进程内接管

GumJS 运行脚本，Java Bridge 改写 ART 方法入口；触发回调后日志原路回传终端。

进程 A：电脑端 frida Windows PID

敲下命令后启动的普通 Python 进程，所有前端解析和客户端通信都在这里完成。

  • Frida CLI（frida-tools）：解析参数、读入脚本、打印日志
  • Python 绑定（frida-python + _frida.pyd）：Python 到 C 的桥
  • 电脑端 Core（静态链接进 _frida.pyd）：管理 USB/ADB 与会话
进程 B：手机端 frida-server Android 独立 PID

以高权限常驻 Android 的原生 ELF 程序，充当电脑和目标 App 之间的“总控与注入器”。

  • ControlService：在 D-Bus 上接收枚举应用、附加进程等指令
  • 设备端 Core / HostSession：匹配包名与 PID，调度会话
  • Linux/Android 后端：注入 agent.so 并与其建立控制通道
进程 C：目标 Android App App 原有 PID

被分析的应用进程本身。Hook 生效的真正战场就在这里，无需重启系统或改 APK。

  • Frida agent（.so）：接收脚本源码、管理脚本生命周期与消息回传
  • Gum & GumJS（静态链接进 agent）：JS 引擎 + 原生插桩能力
  • Java Bridge + ART：定位 Java 方法并把调用转进 JS 回调

版本口径说明：本文的端到端源码行号、链接方式（如 Core 静态链接进 _frida.pyd、Gum/GumJS 静态链接进 agent.so、GumJS 通过 runtime/java.js 加载 Java Bridge）统一固定在 Frida 16.4.7 + frida-tools 12.5.0。主仓库目录结构对照 frida/frida @ a93582c；凡涉及 Frida 17.0+ 将 Java Bridge 拆分为独立包的改动，均会在文中明确标注，避免跨版本混淆。

四个核心子项目：语言、产物与「静态链接」去向

先解一个常见疑惑：为什么在电脑上找不到单独的 libfrida-core.dll，在手机 App 里也看不到单独的 libfrida-gum.so？因为在 16.4.7 默认构建中，Core 被静态链接进了电脑端的 _frida.pyd 和手机端的 frida-server，而 Gum 与 GumJS 则被静态链接进了 frida-agent.so。理解了“构建期合并、运行期分进程加载”，架构图就彻底通了。

语言：Vala 为主（先转译成 C 再编译为原生代码），辅以 C/C++ 与平台注入代码。

Core 原生库
双端复用：电脑端静态链接进 _frida.pyd 发起连接与会话管理；手机端编进 frida-server 响应请求。
frida-server（Android ELF）
独立进程运行在 Android 上，负责枚举应用、按 PID 附加并装载 agent。

04 / End-to-End Source Trace

跨进程源码链路：从命令入口到 ART 方法

这一节把整条链路按三道物理边界拆开讲清楚：每一棒都交代“上一层是谁、参数怎么传过来、本层核心源码在哪、下一棒接给谁”。全部行号均对应 Frida 16.4.7 + frida-tools 12.5.0。

第一棒：电脑进程内（CLI → Python 绑定 → 电脑端 Core）

不论你是敲 frida 命令，还是自己写 Python 脚本 import frida，底层走的是完全相同的调用路径：Python 层通过 CPython 原生扩展 _frida.pyd 直接跳入静态链接的 frida-core C API，全程都在电脑同一个进程内完成。

交接过程：frida 命令由 frida_tools.repl:main 启动。application.py 先通过已选设备查询正在运行的应用，用 -N 给出的包名换到 PID，再调用 self._device.attach(pid)。frida/core.py 把请求交给 C 扩展 extension.c，后者调用静态链接在 _frida.pyd 里的原生函数 frida_device_attach_sync()，正式进入 Vala 实现的 Device.attach()。

交接过程：电脑端 droidy-host-session.vala 让 ADB 选中目标设备并打开通道，在其上建立 Frida 的 D-Bus 连接。手机上独立运行的 server/server.vala 启动着 ControlService，收到应用枚举和附加请求后转交 HostSession。真正干活的是 linux-host-session.vala：先查询 Android 应用列表（L259），再在 perform_attach_to()（L426）里将 frida-agent.so 注入目标 PID，并建立服务端与 agent 之间的控制通道。

第三棒：目标 App 进程内（agent → GumJS → Java Bridge → ART）

frida-agent.so 一旦进入目标 App 的地址空间，真正的脚本运行和 Hook 安装就开始了。记住 App 进程内部清晰的三层分工：

  1. agent 管脚本与通道：接收电脑发来的 hook.js，负责脚本创建、加载、卸载，以及把事件消息送回会话。
  2. GumJS 跑 JS 引擎：由于 16.4.7 默认把 Gum 与 GumJS 静态链接进 agent .so（默认链接配置 · agent 构建定义），agent 直接调用库内 GumJS 运行用户脚本，并把 console.log() 编码成日志消息。
  3. Java Bridge 接管 ART：脚本调用 Java.perform() / Java.use() 时，桥接层通过 JNI 与 ART 内部数据结构交互，完成方法替换。

05 / Minimal Practice

最小实战 Demo：Hook Activity.onResume()

用 8 行 JavaScript 观察任意自有测试 App 的界面恢复时机，并对照看看命令行的每一个参数如何触发前面梳理的整条链路。

这条命令的每一步背后发生了什么？

  1. -U（USB 设备）：让电脑端 Core 选择通过 USB/ADB 连接的 Android 设备，并通过 ADB 通道与手机上已启动的 frida-server 建立 D-Bus 连接。
  2. -N com.example.demo（按包名附加已运行 App）：CLI 先向 frida-server 拉取应用列表，找到 com.example.demo 对应的运行中 PID，再调用 device.attach(pid) 注入 agent.so。（要求 App 提前打开；如果要从冷启动拦截，则改用 -f 让 Frida 负责 spawn 启动并挂起主线程。）
  3. -l hook.js（加载本地脚本）：CLI 读取电脑磁盘上的 hook.js 文本，经会话送入目标 App 内的 agent，由 GumJS 执行。Java.perform() 回调运行完毕时，Activity.onResume() 的 Hook 就安装好了。
  4. 切后台再切回前台（触发与回传）：Android 系统回调 Activity.onResume()，执行流先命中 JS 回调打印 onResume called，再通过 onResume.call(this) 走回原方法；GumJS 的 console.js 把日志封装发回电脑端 CLI，最终出现在终端里。

06 / Deep Dive

底层原理拆解：注入、ART 改写、Native 拦截与横向对比

如果只停留在“.implementation 把入口接到 JS”，很多关键问题依然是黑盒：agent.so 是怎么塞进别人进程的？没有改过 libart.so，Frida 凭什么能改写 Java 方法？它和经典 Xposed 的本质区别又是什么？

6.1 注入机制：frida-server 如何把 agent.so 送进目标进程？

为什么需要独立运行的 frida-server？

Android 应用之间有严格的沙箱和进程隔离。电脑端 CLI 无法直接读写手机 App 的内存，因此需要在设备端运行一个高权限（通常为 root）的 frida-server 进程，由它作为执行者操作目标进程。

注入 agent.so 的四个关键动作

  1. 暂停与存现场：注入器用 ptrace 附加目标进程、暂停执行并备份原寄存器上下文。
  2. 写入与装载：在目标进程内分配执行空间，调用系统动态链接器（dlopen 等路径）将 frida-agent.so 映射进目标 PID。
  3. 恢复原线程：恢复被暂停线程的寄存器并 detach，不阻塞 App 自己的业务线程。
  4. 建立通道：agent 启动内部工作线程，与 frida-server 建立控制通道，等待电脑端下发脚本。

6.2 Java Hook 原理：.implementation 怎么在原生 ART 上生效？

经典 Xposed 靠刷机直接替换 /system/lib64/libart.so 来新增 EnableXposedHook()；而 Frida 面对的是未经修改的原生 ART。它通过 frida-java-bridge 在运行时动态探测当前 Android 版本的 ArtMethod 内存布局，再借助 Gum 的底层读写与原生 Hook 能力完成接管：

Hook 之前 · 原生 ART 执行

调用发起
App / 框架调用 Activity.onResume()
ArtMethod
保留原始访问标志、入口指针与原实现元数据
执行去向
直接进入编译后的机器码（AOT/JIT）或解释器执行原字节码

Hook 之后 · ArtMethodMangler 接管

方法改写
调整目标 ArtMethod 的访问标志与入口指针，把调用引导到桥接分发函数
原实现保留
保存原始 ArtMethod 信息，供回调内 onResume.call(this) 再次调用
优化对抗
配合 ART 反优化 / 禁用内联路径处理，避免调用方绕过方法入口直接内联执行

为什么 Java.perform() 必不可少？ hook.js 最初是在 agent 的工作线程中由 GumJS 执行的，这条线程尚未绑定到 ART 的 JavaVM，也没有可用的 JNIEnv。Java.perform(fn) 会先把当前线程 Attach 到 JVM、等待或定位安全执行上下文，再运行你的回调，确保 Java.use() 能正确解析类加载器并安全操作 Java/ART 对象。

6.3 底层基石：Gum Interceptor 与 Native Hook

Frida 不只能 Hook Java 方法，它最底层的引擎 frida-gum 本身就是一套跨架构（ARM64 / ARM / x86_64）的原生二进制插桩库。当你 Hook 某个 C/C++ 或 .so 导出函数时，Interceptor.attach() 会改写目标函数开头几条机器码，放一条跳转指令到 Gum 动态生成的跳板（trampoline），在 onEnter / onLeave 之间执行 JS 回调，再把被覆盖的原指令迁回跳板执行。即便在纯 Java Hook 场景里，frida-java-bridge 查找 ART 内部符号、读写 ArtMethod 内存、拦截 ART 关键运行时函数，也同样建立在 Gum 提供的原生能力之上。

6.4 横向对照：Frida 与经典 Xposed 的定位差异
