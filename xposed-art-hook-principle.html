Xposed v89 源码解析：ART 方法 Hook 的完整流程

沿着启动、注册和执行这条线读源码。先看 Zygote 怎样初始化 Xposed，再看 Java 回调怎样经 JNI 关联到目标 ArtMethod，最后追踪一次调用如何执行回调并返回。

安装 · 框架文件如何落地

安装 Xposed 框架 ZIP 时，包里的 flash-script.sh 会把框架文件写入 /system。接下来系统启动 Zygote 时，就会运行 Xposed 修改过的 app_process。

  • app_process 是 Zygote 的启动程序。脚本保留原文件，并用软链接把启动路径指向 Xposed 修改后的程序。
  • libart.so 是 Android 的 ART 运行时。脚本装入 Xposed 修改过的版本，后面负责改写方法入口的代码就在这个版本里。
  • libxposed_art.so 是 JNI 桥接库，负责把 Java 层的 Hook 注册请求交给 ART。XposedBridge.jar 提供 Java API，并保存和分发模块回调。

下面是脚本里对应的几行。Zygote 启动后什么时候加载桥接库，见 「准备」。

环境 · Android 与 Xposed 版本

对照基准　本文所有原生 AOSP 片段固定在 android-7.1.2_r39，用于对照同一 Android 小版本。Xposed 实现固定在 Xposed@v89、XposedBridge@v89 和 android_art@v89-sdk25。安装脚本单独标明 XposedTools 的提交。AOSP 标签用于源码对照，发布包的具体上游修订未在本文确认。

源码分布在三个仓库。启动和 JNI 桥用 rovo89/Xposed 的 v89 标签，模块 API 和 Java 回调用 rovo89/XposedBridge 的 v89 标签，运行时改动用 rovo89/android_art 的 v89-sdk25 标签。[查看源码索引]

下文逐行讲解的源码样本是 rovo89 经典 Xposed v89 + Android 7.1.2（API 25）。ART 源码固定到 rovo89/android_art 的 v89-sdk25 标签；该标签目前与 xposed-nougat-mr2 分支头指向同一提交 b23f496。[版本标签与 Android 对照]

Android 7.0 使用 API 24，Android 7.1.x 使用 API 25。两个 API 级别都有 v88、v88.1、v88.2 和 v89 的对应 ART 源码标签。查看版本对照表。

这里的 v89 是 Xposed Framework 版本，sdk25 是 Android 平台 API 级别；它们都不是 Xposed Installer 应用版本，也不能用模块开发用的 api-XX.jar 版本替代。Android 5.x/6.0 有相应经典 Xposed 标签，但 ART 结构和代码细节另论；Android 8.x 的 v90 beta、Frida、LSPosed 均不在本文的逐行实现范围。[Xposed API 版本说明]

准备 · Zygote 初始化桥接层

经典 Xposed 的文件安装完成后，系统启动修改过的 app_process。ART 虚拟机创建时，AppRuntime::onVmCreated 进入 xposed::onVmCreated。后者检测当前运行时为 ART，dlopen 加载 libxposed_art.so，用 dlsym 取得 xposedInitLib，再注册 XposedBridge 的 JNI 方法和 Java 分发入口。这个阶段还没有 Hook 某个应用的 Gate.check。[启动源码]

应用进程由 Zygote 派生时继承已加载的库映射。进入包加载回调后，模块使用该包的类加载器定位示例方法。

模块交出回调

目标包加载时，模块的 handleLoadPackage 创建 XC_MethodHook 对象，调用 findAndHookMethod。这个 API 先解析目标类与方法，再把 Method 和回调交给 XposedBridge.hookMethod。桥接层保存回调集合，并在首次 Hook 该方法时调用 native 安装逻辑。此时 beforeHookedMethod 只是对象里的方法定义，尚未执行。[API 与桥接源码]

模块 Java 示例 · IXposedHookLoadPackage 实现类的 handleLoadPackage()
public void handleLoadPackage(LoadPackageParam lp) throws Throwable {
    // 只在示例应用的包加载时注册。
    if (!"com.example.target".equals(lp.packageName)) return;

    // 用该应用的类加载器定位 Gate，并用参数类型选定方法。
    XposedHelpers.findAndHookMethod(
        "com.example.target.Gate", lp.classLoader,
        "check", String.class,
        new XC_MethodHook() {
            protected void beforeHookedMethod(MethodHookParam p) {
                // 命中 Hook 后才执行。这里设置返回值并跳过原方法。
                if ("block".equals(p.args[0])) p.setResult(false);
            }
        });
}

假设 Gate.check(String) 返回 boolean。上面的代码只用于说明 API 调用；目标类名和类加载器需与示例应用一致。

首次注册进入 native 安装

第一段在 Java 类 XposedBridge 的 hookMethod() 里，它调用同一个类声明的 native 方法 hookMethodNative()。第二段是该 native 方法在 C++ 的实现，函数名为 xposed::XposedBridge_hookMethodNative()。Xposed 在初始化时通过 JNI 注册表把这两个符号绑定起来。[Java native 声明] [JNI 注册表]

XposedBridge.hookMethod 经 JNI 调用 hookMethodNative。Xposed 的 libxposed_art.cpp 用 ArtMethod::FromReflectedMethod 把 Java 反射 Method 转成目标 ArtMethod*，再调用 Xposed 加入 ART fork 的 EnableXposedHook。[native 源码][ART fork]

FromReflectedMethod 属于 ART。EnableXposedHook 是经典 Xposed 加入 ART fork 的逻辑。

“复制原方法”究竟复制了什么？

看动画 · 安装 Hook

EnableXposedHook 先用 CreateRuntimeMethod 分配新的 ArtMethod，再用 CopyFrom 复制目标 ArtMethod 的结构字节。复制的是方法元数据与入口指针，不是复制 DEX 字节码或整块机器码。备份对象被标记为 kAccXposedOriginalMethod。[CopyFrom 源码]

如果启用了 JIT，且刚复制的 quick 入口位于 JIT 代码缓存，CopyFrom() 会把备份的 quick 入口改成解释器桥。之后还会单独清除非 native 方法的 profiling 指针，并把备份的热度计数清零。[源码]

框架还创建指向备份对象的反射 Method，并将它、模块回调信息和备份 ArtMethod* 放进 XposedHookInfo。这份信息在后续分发和调用原方法时使用。[ART fork]

为什么要改 quick entry point？

仅把回调存进 Java 集合，应用执行 Gate.check() 时不会自动进入 Xposed。这个 ART 版本的 ArtMethod 包含 entry_point_from_quick_compiled_code_，quick 调用可通过它转到编译代码或运行时桥接 stub。经典 Xposed 把目标方法的这个入口改成 GetQuickProxyInvokeHandler() 返回的代理 stub 地址，才建立“目标调用 → 框架”的跳转。[字段定义][改写源码]

三行代码改的是同一个目标 ArtMethod 的三个位置

  1. 599 行存数据地址。 entry_point_from_jni_ 槽里写入的是 XposedHookInfo*。执行进入代理后，GetXposedHookInfo() 从这个槽读回指针，分发函数再用其中的备份反射对象和回调信息组装 Java 参数。[读回指针] [组装分发参数]
  2. 600 行改调用去向。 entry_point_from_quick_compiled_code_ 存入代理 stub 的代码地址。后面在 ARM64 的 quick 调用路径上，ldr 从这个槽把新地址读进 x9，blr x9 就跳进代理 stub。[查看调用侧]
  3. 601 行清掉目标对象的 DEX 代码偏移。 dex_code_item_offset_ 是 code_item 在 DEX 文件里的偏移。设为 0 后，通过这个目标对象查 GetCodeItem() 会得到 nullptr。这行只改目标对象的字段，DEX 文件的原指令没有被擦除。前面第 567 行已经复制了方法对象，所以对原本带 DEX 方法体的 Java 方法，备份对象仍有原偏移，执行原方法可以走备份对象。[读取偏移] [零偏移的含义]

展开看三个 setter 的实现

599 行 · JNI 槽怎样写入和读回

EnableXposedHook() 的第 599 行先调用 SetEntryPointFromJniPtrSize()。传进来的 entrypoint 就是 hook_info 的地址，pointer_size 来自 sizeof(void*)。

reinterpret_cast<uint8_t*>(hook_info) 转换指针类型，地址值保持相同。sizeof(void*) 指定写入的指针宽度，64 位写 8 字节，32 位写 4 字节。

进入 setter 后，第 594 行把 EntryPointFromJniOffset(pointer_size) 写在 SetNativePointer() 的第一个实参里。C++ 要先算出这个实参，才能调用外层函数。把第 594 行拆开看，就是下面两步。

第 594 行拆解 · 等价写法
const MemberOffset offset = EntryPointFromJniOffset(pointer_size);
SetNativePointer(offset, entrypoint, pointer_size);

第一步得到的是相对目标 ArtMethod 起点的字节偏移，第二步才把 hook_info 指针写进那个槽。下面按调用顺序列出 setter 和算偏移的函数。最后的 GetXposedHookInfo() 是之后分发时才走的读回路径。

600 行 · 代理地址从哪里来，又写到哪里

内层的 GetQuickProxyInvokeHandler() 取汇编符号 art_quick_proxy_invoke_handler 的地址。外层 setter 把这个地址写到 quick 槽。下一次调用从该槽取到的就是这个地址。

以 ARM64 为例，art_quick_proxy_invoke_handler 指向已加载的 libart.so 里这段汇编的入口，也就是下面 ENTRY 标出的地址。第 600 行把这个地址存到 quick 槽。之后调用方命中这个入口时，先跑汇编 stub，再由第 1813 行的 bl 调用 C++ 函数 artQuickProxyInvokeHandler()。C++ 处理器识别出 Xposed 方法后，再进入 Java 回调分发。[接着看 C++ 和 Java 分发]

599、600 行共用 · SetNativePointer() 最终写哪

两行走的是同一个写入函数。用 ArtMethod 对象地址加上字段偏移，得到槽的地址，再按指针宽度写入 4 或 8 字节。两个调用的区别在传入的字段偏移和指针值。

601 行 · 为什么写 0 之后查不到方法体

这一行是普通整数赋值。后续查方法体时，ArtMethod::GetCodeItem() 把偏移传给 DEX 查询函数。偏移为 0 时，查询直接返回空指针。备份 ArtMethod 是改写前复制的，原偏移仍在备份里。

ArtMethod::Invoke() 有解释执行分支。走到下面的 quick 分支时，它按目标是否为静态方法选择不同的 stub，并把 C++ 的 this 作为第一个参数传入。这里的 this 是 目标 ArtMethod*，Java 接收者已经放在实参里。普通的 Java 编译代码调用还可以直接从调用点进入目标代码，内联时甚至可能省去独立调用。

ARM64 汇编 stub 用 bl artQuickProxyInvokeHandler 进入这个函数。x0 对应目标方法，x1 对应实例方法的接收者，汇编再把当前线程和栈指针放进 x2、x3。[查看汇编调用处]

  1. 先认方法。 第 847 行用 IsXposedHookedMethod() 检查目标方法的标志。这里读的正是安装 Hook 时第 605 行写入的 kAccXposedHookedMethod，决定后面走 Xposed 分支还是普通动态代理分支。
  2. 再取实参。 BuildQuickArgumentVisitor 根据 shorty 类型描述从 quick 调用帧读取实参，整理成 std::vector<jvalue>。对象实参转成 JNI 局部引用，方便后续分发期间安全跨过 GC。实例方法的接收者另存为 rcvr_jobj。[参数读取与引用修正]
  3. 按标记分发。 Xposed 方法在第 884 行走 InvokeXposedHandleHookedMethod()，普通动态代理在第 899 行走 InvokeProxyInvocationHandler()。两条路径都会修正调用帧中的对象引用，把结果交回汇编 stub。

第 360 行怎样执行原来的方法？

谁调用 C++ 的 XposedBridge_invokeOriginalMethodNative()？ 调用点就在 Java 的 XposedBridge.handleHookedMethod() 第 360 行。before 执行完且 returnEarly 为 false 时，它调用同一个类的 invokeOriginalMethodNative()。这个 Java 方法在第 429 行声明为 native。Xposed 初始化时通过 JNI 注册表把它绑定到 libxposed_art.cpp 第 98 行的 C++ 函数，因此 ART 执行这次 Java 调用时会进入该函数。[Java 调用点] [native 声明] [JNI 注册表]

  1. Java 拿到的 method 已经指向备份。 安装 Hook 时，ART 用备份 ArtMethod 创建反射对象并存进 hook_info->reflected_method。分发前，JNI 把该对象放入 invocation_args[0]，又在 invocation_args[1] 放入 1。因此 Java 的 method 是备份的反射对象，originalMethodId 在这条 ART 路径上作为 native 的 isResolved 标志。[创建并保存备份]
  2. native 直接使用这个备份。 第 360 行调用 invokeOriginalMethodNative(method, …)。因为 isResolved == 1，JNI 实现跳过重新找备份的分支，直接把反射对象、接收者和可能被 before 修改过的参数传给 ART 的 InvokeMethod()。

谁调用 FindVirtualMethodForVirtualOrInterface()？

上面的 libxposed_art.cpp 第 108 行把备份的反射对象交给 art::InvokeMethod()。进到下面的 reflection.cc，第 578 行从反射对象取出 ArtMethod* m。如果示例中的 Gate.check() 是实例方法，第 605 行就通过接收者的实际类调用 FindVirtualMethodForVirtualOrInterface(m, …)。

为什么反射调用不会从虚表找回被 Hook 的目标？ InvokeMethod() 从反射对象解出备份 ArtMethod。对于实例方法，它还会走 FindVirtualMethodForVirtualOrInterface()。备份对象在创建时已加上 kAccXposedOriginalMethod，而 IsDirectOrOriginal() 识别这个标记，所以函数直接返回传入的备份，跳过后面的虚表查找。随后 InvokeWithArgArray() 调用这个备份对象的 Invoke()，沿备份自身的执行入口运行原实现。[取出 ArtMethod、处理实例方法] [识别原方法标记] [提交调用] [进入 Invoke]

原方法的结果或异常回到同一个 MethodHookParam，再逆序执行已运行过 before 的那些回调所对应的 after，最后返回结果或抛出异常。[原方法返回与 after]

如果模块主动调用公开的 XposedBridge.invokeOriginalMethod()，Java 会传入 0。这时 JNI 才会检查传入的方法是否被 Hook，并从 XposedHookInfo 找到对应备份。[公开 API 传入 0]

回调结果怎样回到调用方？

以 Gate.check("block") 为例，before 设定 false 并跳过原方法。如果后续 after 保留了这个结果，它就沿下列路径回到调用方。

  1. Java 返回装箱结果。 handleHookedMethod() 的返回类型是 Object，所以此时返回的是 Boolean.FALSE。JNI 的 CallStaticObjectMethodA() 收到这个对象。[Java 返回位置]
  2. ART 拆箱。 InvokeXposedHandleHookedMethod() 按目标方法的返回类型调用 UnboxPrimitiveForResult()，把 Boolean 转回原始 boolean 的值，放进 JValue。C++ 代理处理器再用 result.GetJ() 把结果位交给汇编。[ART 拆箱源码] [C++ 返回源码]
  3. 汇编返回。 ARM64 代理 stub 确认没有待处理异常后恢复现场并执行 ret。沿上面展示的反射调用路径，它回到 blr x9 的下一条指令，调用 stub 再把 x0 里的结果写到 JValue* result。如果有待处理异常，代理 stub 转到异常分发分支。[代理返回与异常] [调用 stub 保存返回值]

本文举例用的是 Method.invoke()。ART 收到调用 stub 写回的 JValue 之后，还会把基本类型装箱再返回给反射调用方。示例里这里会再次得到 Boolean。如果调用抛出异常，反射层会把它包装成 InvocationTargetException。[反射层的返回与异常包装]

JIT、AOT 与内联的边界

Hook 能否命中，关键是调用是否经过被改写的目标方法入口。JIT/AOT 已编译的调用者可能保留旧状态，因此经典 Xposed 安装时会使相关调用者失效、处理 JIT 代码和线程栈。若调用方已把目标方法内联进自己的代码，就可能没有独立的 Gate.check 调用边可拦截；此时需要考虑对调用方去优化或调整 Hook 点。[ART fork][LSPlant 的内联说明]
