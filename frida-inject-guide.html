frida-server 如何把 frida-agent.so 注入目标 App？

接着上一篇停下的位置——linux-host-session.vala::perform_attach_to(pid)——深入 frida-core 源码，拆开整个跨进程注入黑盒：Frida 如何用 PTRACE_SEIZE + 假返回地址 0x320 远程调用、bootstrapper + loader 两阶段无依赖二进制、memfd + SCM_RIGHTS 跨进程传 FD，以及伪装 libc->close 地址绕过 Android Linker Namespace，在毫秒级暂停内将 frida-agent.so 送进目标进程并点亮 D-Bus 会话。

01 / Mental Model

先破除一个老误区：现代 Frida 绝不在 ptrace 里直接调 dlopen

网上很多旧文章把 Android 注入概括成“ptrace 停住 App 主线程 → 远程调用 dlopen('/data/local/tmp/frida-agent.so') → 恢复运行”。这套传统写法在现代 Android（Android 7+ Linker Namespace、严格 SELinux、多线程锁冲突）上几乎处处碰壁。

❌ 传统直调 dlopen 的四个死穴

  • 死锁风险：被暂停的线程可能正好拿着 linker / malloc 锁，在 ptrace 停顿状态里直接调 dlopen 极易死锁或卡死 UI 触发 ANR。
  • Linker Namespace 拦截：Android 7+ 的 __loader_dlopen 会检查调用者返回地址所属的 namespace，匿名可执行页里的 shellcode 直接调会被拒绝加载。
  • SELinux 文件域限制：把 .so 写到 /data/local/tmp 等目录，目标 App 的 SELinux 域可能根本无权读取或 mmap(PROT_EXEC)。
  • 目标 libc 位置未知：不同容器、chroot 或早期进程里，目标的 libc.so / linker64 映射甚至与 frida-server 不同，盲算偏移直接崩溃。

✅ Frida 16.4.7 的真实四重破局设计

  • ptrace 只干极轻的活：loader 入口 frida_load() 只执行一行 pthread_create() 就立刻返回并 DETACH，真正耗时的 dlopen 全部放到独立后台线程里跑。
  • 伪装调用者地址：调用 Android linker 的 __loader_dlopen 时，把第 3 个参数 caller_addr 填成 libc->close 的地址，合法借用系统默认 namespace。
  • memfd + SCM_RIGHTS 传 FD：agent.so 优先塞进内存文件 memfd，通过 Unix Socket 跨进程把 FD 送进目标 App，再由 App 自己 dlopen("/proc/self/fd/<N>")。
  • 两阶段独立汇编载荷：预先用 nolibc 编译好 bootstrapper-arm64.bin 和 loader-arm64.bin；阶段一先在目标进程内现场查 /proc/self/auxv 与 ELF 导出表，摸清所有函数地址。

03 / Line-by-Line Source Walkthrough

逐行源码拆解：从 perform_attach_to() 到 frida_agent_main()

下面全部代码片段与行号均直接取自 frida/frida-core 提交 78ff6e5b（Frida 16.4.7）。每一段都会先交代“上一层怎么交接过来”，再看关键行，最后指向下一层接续点。

3.1 入口接缝：perform_attach_to() 与 memfd 备弹

上一篇我们追到电脑端发来 attach(pid) 请求，手机上的 frida-server 最终进入 linux-host-session.vala 的 perform_attach_to()。它只做两件事：把 agent 资源注入目标 PID（指定入口符号 "frida_agent_main" 并开启 CONTROL_CHANNEL 标志），然后立刻向 linjector 索要代表控制通道的 IOStream——后面整个 D-Bus 会话就跑在这条流上。

紧接着进入 linjector.vala 的 inject_library_resource()。注意第 86–95 行：只要 Linux 内核支持 memfd_create（现代 Android 内核普遍支持），Frida 根本不会把 frida-agent-64.so 解压写到磁盘，而是直接拿一个匿名内存文件描述符（resource.get_memfd()），连同目标 PID、入口名一起传给 helper.inject_library()。只有老内核不支持 memfd 时才回退到临时目录文件。

3.2 ptrace 劫持与 RemoteCall：假返回地址 0x320 的妙用

进入 frida-helper-backend.vala 后，InjectTask 打开一个 InjectSession（继承自 SeizeSession）。注意两个非常工程化的细节：

  1. 优先使用 PTRACE_SEIZE + PTRACE_INTERRUPT（Linux 3.4+）：相比老式的 PTRACE_ATTACH（它会直接往目标发 SIGSTOP，可能被 App 信号处理器或异常状态干扰），SEIZE 可以静默接管进程，再配合 INTERRUPT 干净地把目标线程停下来，并用 PTRACE_GETREGSET 备份完整的通用寄存器与浮点寄存器（saved_registers）。
  2. 怎样让目标线程执行完一个函数后精准把控制权交还给 frida-server？ 看下面 RemoteCall::execute() 的 ARM64 实现：它把函数参数依次放进 x0..x5，把 PC 改成目标函数地址，然后把返回地址寄存器 LR (x30) 设成一个必然触发段错误的非法地址 DUMMY_RETURN_ADDRESS = 0x320！等目标函数执行到 RET 跳去 0x320 时，CPU 立刻触发 SIGSEGV 并被 ptrace 截获——frida-server 只要检查停下时的 PC == 0x320，就知道函数正常返回了，立刻从 x0 读走返回值，并把之前保存的 saved_registers 写回去，仿佛什么都没发生过！

怎么先在目标进程里拿到第一块能写代码的 RWX 内存？（frida-helper-backend.vala L1082–1122）

① 常规快路径（Android 绝大多数情况）：frida-server 查 /proc/<pid>/maps 发现目标 App 映射的是和自己同一份系统 libc.so，直接用「目标 libc 基址 + 本机 mmap 偏移」算出 remote_mmap，通过一次 RemoteCall 在目标进程里调 mmap(RWX) 拿到 allocation_base。

② 兜底冷路径（ProcessCodeSwapScope，L2254–2291）：如果目标进程与服务端用的不是同一份 libc（例如容器/静态链接程序），Frida 会先用 ThreadSuspendScope 冻结目标进程的所有其他线程，借用目标进程某段 r-x 代码页临时覆盖写入 bootstrapper，让 bootstrapper 自己用系统调用 mmap 申请 RWX 内存，然后再把原代码页原样写回并恢复所有线程！

3.3 阶段一 bootstrapper.c：不靠 libc 摸清目标进程全部关键函数

拿到目标进程里的一块 RWX 内存（allocation_base）后，frida-server 把预先编译好的无 libc 机器码 bootstrapper-arm64.bin 写进去，并在目标线程栈上留出 FridaBootstrapContext 与 FridaLibcApi 结构体空间，通过 RemoteCall 调用入口函数 frida_bootstrap(ctx)。

frida_bootstrap() 返回后，frida-server 从目标栈上把填好的 FridaBootstrapContext 和 FridaLibcApi 读回本地。这里还有一个非常隐蔽的跨内核优化（frida-helper-backend.vala L1246–1279）：

  • Linux 5.6+（现代 Android 内核）：bootstrapper 在目标进程里建好了 ctrlfds[0..1]，frida-server 直接调用系统调用 pidfd_open(pid) + pidfd_getfd(ctrlfds[0])，凭空把目标进程里的 ctrlfds[0] 复制一份到自己进程里！于是两个进程之间瞬间就有一条完全匿名的 Unix Socket 控制通道，连 abstract socket 名称都不会出现在 /proc/net/unix 里。
  • 旧内核兜底：如果不支持 pidfd_getfd，frida-server 才监听一个 abstract Unix socket（/frida-<随机UUID>），等下一阶段的 loader 主动连上来。

3.4 阶段二 loader.c：秒退主线程 + SCM_RIGHTS 收 FD + 伪装 libc->close

接下来 InjectSession.inject()（L908–925）把阶段二的 loader-arm64.bin、FridaLoaderContext、FridaLibcApi 以及 "frida_agent_main" 字符串覆盖写进刚才那块 RWX 内存，并用最后一次 RemoteCall 调用 frida_load(ctx)。

看下面 loader.c 第 61–64 行——这就是整个注入最优雅的地方：被 ptrace 劫持的 App 主线程只执行了 1 行 pthread_create 就立刻返回，随后 frida-server 还原主线程寄存器并结束 ptrace。真正的 dlopen 和 frida_agent_main 全部在新建的后台 worker 线程（frida_main）里安静执行！

对照服务端发 FD 的另一端：就在 loader 执行第 110 行与第 131 行的 frida_receive_fd() 时，frida-server 侧的 RemoteAgent.start()（frida-helper-backend.vala L1513–1557）正在按完全相同的顺序调两次 frida_ctrl.send_fd()：第一枚发的是 spec.library_so.get_fd()（agent.so 的 memfd），第二枚发的是刚建好的 agent_ctrl socketpair 的对端（agent_ctrlfd_for_peer）。

3.5 落地收尾：frida_agent_main() 点亮 D-Bus 会话与内部线程

loader.c 第 143 行调用 frida_agent_main()，对应 lib/agent/agent.vala 里的 Frida.Agent.main() → Runner.create_and_run()。它把收到的 agent_ctrlfd 拼成传输地址 "socket:<fd>..."，顺手把自身代码内存区加入 Gum.Cloak，随后在 GLib MainLoop 里建好 DBusConnection 并激活 GumJS 调度线程——到这里，就和我们上一篇 《Frida 里的 D-Bus 到底是什么？》 与第一篇 《Frida Android 入门与源码仓库拆解》 彻底严丝合缝地接上了！

05 / Attach vs Spawn on Android

延伸追问：-N（Attach）和 -f（Spawn）在 Android 上差在哪？

对于普通 Linux 命令行程序，Frida 做 spawn 很简单——直接 fork() + PTRACE_TRACEME + execve() 把新进程停在入口即可（frida-helper-backend.vala L32–97）。但 Android App 根本不能直接 execve，它们全是由 zygote / zygote64（以及 Android 10+ 的 usap32 / usap64 预孵进程池）fork 出来的！

因此 linux-host-session.vala 专门为 Android 写了一套 RoboLauncher（L589–799）：

  1. 先往 zygote / zygote64 / usap32 / usap64 注入 ZygoteAgent（L730–740）并开启 child gating，监视它们什么时候 fork 并特化（specialize）出目标 App 子进程。
  2. 借助注入到 system_server 的 SystemServerAgent，先调用 stop_package() 杀掉旧进程，再调用 start_package() 让 Android AMS 正规拉起该 App（L623–624）。
  3. 在特化完成的瞬间挂起子进程：ZygoteAgent 捕获到目标包名的新子进程后，RoboLauncher.try_handle_child() 把新 PID 返回给 CLI；此时 App 主线程还停在非常早期（业务 Application.onCreate() 尚未执行），CLI 趁机 attach(pid) 加载你的 hook.js，等脚本装完 Hook 再调用 resume(pid) 放行！
对比维度 Attach 模式（frida -U -N 包名） Spawn 模式（frida -U -f 包名）
目标进程前提 App 必须已经在运行，已有现成 PID 先 stop_package 杀掉旧进程，再由系统重新冷启动
是否注入系统进程 否，只注入目标 App 本身（加上枚举应用时可能按需借助 system_server） 是，需向 zygote/zygote64/usap* 注入 ZygoteAgent，并由 SystemServerAgent 启停包
脚本介入时机 随时介入，但错过启动早期逻辑（如 JNI_OnLoad、壳解密、早期初始化） 子进程刚特化即挂起，可在 Application.onCreate() 与早期 .so 加载前下钩
底层注入 agent.so perform_attach_to() → 本文全套两阶段注入 拿到挂起的新 PID 后，同样走 perform_attach_to() 注入并加载脚本，最后 resume

06 / Forensic Footprint

原理反推：一次注入在目标 App 里留下了哪些真实痕迹？

懂了上面 5 节的源码实现，很多一线逆向与风控文章里列举的“Frida 检测点”就不再是死记硬背的清单，而是上述机制的必然副产物：

1. /proc/pid/maps 里的匿名 RWX 与 memfd 映射

阶段一申请的 allocation_base 是一块匿名 rwxp 内存页；随后 dlopen("/proc/self/fd/N") 加载 memfd 里的 agent.so 后，在 maps 中会留下类似 /memfd:frida-agent-64.so (deleted) 的映射项（老内核无 memfd 时则是临时目录里的 frida-agent-*.so）。

2. /proc/pid/task/*/comm 里的新增线程

阶段二 frida_load() 新建了 worker 线程，进入 frida_agent_main() 后 GLib 与 GumJS 又会拉起 gmain、gdbus、gum-js-loop、pool-frida 等内部线程。虽然 agent.vala 调了 Gum.Cloak，但那是给 Frida 自己 API 过滤用的，外部直接读 /proc 依然可见。

3. /proc/pid/status 的 TracerPid 短暂窗口

从 PTRACE_SEIZE 到阶段二 DETACH 的短短几毫秒内，目标进程内核状态里的 TracerPid 会变成 frida-server（或 frida-helper）的 PID。高频轮询 TracerPid 的保护线程有可能在这个窗口期抓到痕迹。

4. /proc/pid/fd、Unix Socket 与 27042 端口

目标进程内多出了 ctrlfd 与 agent_ctrlfd（指向匿名 Unix Socket）；在不支持 pidfd_getfd 的老内核上，/proc/net/unix 还会短暂出现 @/frida-<uuid>；而设备端常驻的 frida-server 默认监听 27042 并响应 D-Bus AUTH（详见 D-Bus 专题）。
