frida-server 如何把 frida-agent.so 注入目标 App？

看复杂的底层源码最怕“一上来就掉进寄存器和系统调用的细节泥潭”。本文严格分成两层来写：第一部分只讲“要做什么”（不堆砌任何技术名词，用最直白的大白话把从附加进程、开辟内存、写入并执行机器码、创建 socketpair，到把 frida-agent.so 传过去加载执行的 7 个动作 一条线串起来）；第二部分再讲“怎么做到”（围绕这 7 个动作，把每一处寄存器改写、内存排布、内核句柄传递与源码逐一展开）。

01 / Part I · What Needs To Be Done

第一部分：整体主干流程（先不看技术细节，只看每一步“要做什么”）

我们的目标非常纯粹：让正在运行的目标 App 加载并运行 frida-agent.so。为了实现这个目标，frida-server 依次做了下面 1 个前置准备 + 7 个连续动作（点击任意一步可直接跳到第二部分看它的底层技术细节）：

🤔 为什么要分这么几步走？不能在动作 2 直接让目标进程加载 frida-agent.so 吗？

  • 原因 1（先得找函数地址）：要想在目标进程里加载 .so 或建线程，必须调用目标进程里的系统函数（如 dlopen、pthread_create），但我们一开始并不知道它们在目标进程内存的什么位置——所以必须先有动作 2（开辟内存）和动作 3（写一段探路机器码进去把函数地址找出来）。
  • 原因 2（不能一直卡住主线程）：加载 20MB 的 frida-agent.so 很耗时，而且被暂停的主线程可能正拿着系统锁；如果在主线程里硬加载，App 很容易卡死——所以必须有动作 4（拉起一个独立的后台线程来干重活，先把主线程放行）。
  • 原因 3（不落盘传递 `.so`）：后台线程跑起来后，为了让它在不读写手机磁盘的前提下拿到 frida-agent.so，才需要借用动作 3 建好的 socketpair 管道，在动作 5 ~ 7 里把 `.so` 从内存传过去并映射启动。

📦 frida-server 肚子里自带的三样“载荷”分别在哪一步登场？

  • 第一段机器码 bootstrapper.bin（在动作 3 写入执行）：极小的纯机器码，负责在目标进程里搜寻函数地址、创建 socketpair 通信管道。
  • 第二段机器码 loader.bin（在动作 4 写入执行）：同样是极小的纯机器码，负责在目标进程里创建后台线程，并指挥后台线程完成动作 5 ~ 7（接收、映射并启动 frida-agent.so）。
  • 核心动态库 frida-agent.so（在动作 5 传给目标进程，动作 6 ~ 7 启动）：真正的 Hook 引擎与 JS 运行时所在的主体库。

📍 动作 2：开辟内存

【在哪里运行】：🟦 frida-server 改寄存器发号施令 ➔ 🟧 目标 App 主线程真正执行 mmap() 开辟内存 ➔ 🟦 frida-server 从 x0 读回新内存地址。
【这一步要做什么】：在目标进程自己的地址空间里，开辟一块可读、可写、可执行（RWX）的空白内存区，用来放后面要写入的机器码。

📍 动作 3：写入第一段机器码、执行机器码、创建 socketpair

【在哪里运行】：🟦 frida-server 把 bootstrapper.bin 写进目标内存 ➔ 🟧 目标 App 主线程执行这段机器码（搜函数地址 + 在目标 App 内创建 socketpair） ➔ 🟦 frida-server 用 pidfd_getfd 把 socketpair 的一端复制到自己进程。
【这一步要做什么】：往动作 2 刚开辟出来的内存里写入第一段探路机器码并让目标 App 执行，在目标进程内部找齐后面要用到的系统函数地址，并创建一对 socketpair 建立与 frida-server 的跨进程通信管道。

【在哪里运行】：🟦 frida-server 把 loader.bin 覆盖写进目标内存 ➔ 🟧 目标 App 主线程执行 frida_load() 拉起后台线程 ➔ 🟦 frida-server 还原主线程寄存器并脱离 ptrace（从此目标 App 主线程恢复自由，接力棒交给目标 App 新建的后台线程！）。

📍 动作 5：通过管道把 frida-agent.so 传给目标后台线程

【在哪里运行】：🟦 frida-server 创建 memfd 并调 sendmsg 发送句柄 ➔ 🟩 目标 App 后台线程 (frida_main) 调 recvmsg 接收句柄。
【这一步要做什么】：在不往手机磁盘写任何文件的前提下，把 frida-server 肚子里的 frida-agent.so 通过动作 3 建好的管道传给动作 4 刚拉起的目标后台线程。

📍 动作 6：后台线程将 frida-agent.so 映射进内存并执行初始化

【在哪里运行】：🟩 目标 App 后台线程圈出虚拟地址回报基址 ➔ 🟦 frida-server 按该基址算好 ELF 重定位并下发映射指令 ➔ 🟩 目标 App 后台线程执行段映射、刷缓存并调构造函数。
【这一步要做什么】：目标后台线程拿到 frida-agent.so 的文件句柄后，把它的代码段与数据段装载进目标进程内存，完成重定位并执行它的初始化构造函数。

📍 动作 7：启动 frida-agent.so 主入口函数，建立长期通信连接

【在哪里运行】：🟦 frida-server 经管道传入新句柄 agent_ctrlfd ➔ 🟩 目标 App 后台线程跳入 frida_agent_main() 启动 Agent 与 JS 引擎。
【这一步要做什么】：目标 App 的后台线程调用 frida-agent.so 的主入口函数 frida_agent_main()，与 frida-server 建立正式的控制连接，并启动 JS 引擎等待执行 Hook 脚本。

05 / Attach vs Zymbiote Spawn

Frida 17 的另一大进化：-f（Spawn）如何用 Zymbiote 取代 Zygote 注入？

在 Android 上，App 全是由 zygote / zygote64（以及 Android 10+ 的 usap32 / usap64 进程池、甚至 com.android.chrome_zygote）fork 出来的。Frida 16 时代做 -f Spawn 需要往 Zygote 注入庞大的 frida-agent.so；而 Frida 17.27.5 彻底改用极轻量的 Zymbiote（zymbiote-arm64.elf）！

它的工作流非常干净：当 frida -U -f com.example.demo 触发 RoboLauncher.spawn() 时，SystemServerAgent 先停止并重新拉起目标包；一旦 Zygote fork 出新子进程并调用 android.os.Process.setArgV0("com.example.demo")，被替换的槽位就会触发 Zymbiote 连回 frida-server（ZymbioteConnection 发送 Hello），在业务代码运行前原地暂停，等 CLI 对这个新 PID 走完前文的 perform_attach_to() 并装好脚本后，再发送 resume 放行！

对比维度 Attach 模式（frida -U -N 包名） Spawn 模式（frida -U -f 包名）
前置动作 App 必须已在运行，直接按包名找到现有 PID 向 zygote/usap/chrome_zygote 植入极小 Zymbiote 补丁，再借 system_server 重启 App
对其他 App 的影响 零影响 相比 Frida 16 不再往 Zygote 注入庞大 frida-agent.so，非目标 App 收到 resume 即直接继续
脚本介入时机 随时附加，但错过 JNI_OnLoad / 早期初始化 在 setArgV0() 时即挂起，早于 Application.onCreate() 与业务 .so 加载
载入 frida-agent.so perform_attach_to() → 本文两阶段自映射注入 捕获挂起 PID 后，同样走 perform_attach_to() 两阶段自映射注入，装完脚本再放行

06 / Forensic Footprint

原理反推：Frida 17.27.5 注入后，进程里还留有哪些痕迹？

启用默认 HAVE_MAPPER 自映射后，痕迹相比老版本发生了明显变化——从 linker 链表里消失了，但内核视图里仍有迹可循：

1. Linker soinfo 隐身，但 /proc/pid/maps 仍有映射

因为 frida_map_agent() 绕过了 dlopen(agent.so)，通过 dl_iterate_phdr 或 Android linker 内部 soinfo 链表找不到 frida-agent.so；但在内核 /proc/pid/maps 中，阶段一的匿名 rwxp 页、MAP_FIXED 映射的 /memfd:... (deleted) 代码段与匿名可写数据段依然存在。

2. /proc/pid/task/*/comm 里的后台线程

阶段二拉起 worker 线程，进入 frida_agent_main() 后 GLib 和 GumJS 仍会创建 gmain、gdbus、gum-js-loop、pool-frida 等线程；Gum.Cloak 只过滤 Frida 自身的 API 枚举，外部直接遍历 /proc/pid/task 依然可见。

3. TracerPid 短暂窗口与匿名 Unix Socket

PTRACE_SEIZE 到 DETACH 的几毫秒内 TracerPid 非 0；进程内新增的 ctrlfd / agent_ctrlfd 在 /proc/pid/fd 中体现为匿名 Unix Socket（Linux 5.6+ 因使用 pidfd_getfd，不会在 /proc/net/unix 留下 @/frida-* 名称）。

4. frida-server 27042 端口与 Zymbiote 补丁

设备端常驻进程默认监听 27042 并响应 D-Bus AUTH（详见 D-Bus 专题）；若使用过 -f Spawn，Zygote 内存里的 setArgV0 槽位和 Zymbiote 载荷也会伴随进程生命周期存在。
