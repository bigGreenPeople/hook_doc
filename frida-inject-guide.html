frida-server 如何把 frida-agent.so 注入目标 App？

接着上一篇停下的位置——linux-host-session.vala::perform_attach_to(pid)——直接基于最新正式版 Frida 17.27.5 逐行拆解跨进程注入黑盒：不仅有 PTRACE_SEIZE + 假返回地址 0x320 远程调用、bootstrapper + loader 两阶段无依赖二进制和 memfd + SCM_RIGHTS 传 FD，更要看清 Frida 17 在 Linux/Android 默认开启的 HAVE_MAPPER 自映射加载器（绕过系统 dlopen，零 soinfo 登记），以及彻底取代旧版 Zygote 注入的 Zymbiote 机制。

01 / Mental Model

先破除两代误区：Frida 17 连 dlopen(frida-agent.so) 都默认绕过了

网上很多老文章还停留在“ptrace 暂停主线程 → 远程调用 dlopen('/data/local/tmp/frida-agent.so')”的旧印象里。到了最新版的 Frida 17.27.5，整个注入体系其实已经演进成了两阶段无依赖载荷 + 默认用户态 ELF 自映射（Mapper）。

❌ 传统直调 dlopen 的四个死穴

  • 死锁与 ANR：被暂停的线程可能正持有 linker / malloc 锁，在 ptrace 停顿期间直接调 dlopen 极易死锁。
  • Linker 登记与 Namespace 拦截：Android 7+ __loader_dlopen 会校验调用者地址所属 namespace；而且只要走了系统 dlopen，frida-agent.so 就会被写进 linker 的 soinfo / r_debug / dl_iterate_phdr 链表。
  • SELinux 文件域限制：把 .so 落盘到 /data/local/tmp 极易被目标 App 的 SELinux 策略拒绝读取或 PROT_EXEC。
  • 老版 Zygote 注入过重：Frida 16 及以前做 -f Spawn 需要往 zygote 注入完整的 frida-agent.so。

✅ Frida 17.27.5 的真实四重破局

  • ptrace 秒退主线程：frida_load() 只执行 1 行 pthread_create() 就立刻返回并 DETACH，耗时加载全在独立后台 worker 线程中完成。
  • 默认 HAVE_MAPPER 自映射（核心新特性）：meson.build:1019 对 Linux/Android 默认开启 HAVE_MAPPER——frida-server 在服务端算好重定位，遥控 loader 用 mmap/mprotect + ARM64 刷 I-Cache 直接把 frida-agent.so 映射执行，不经过系统 dlopen，不进入 linker soinfo 链表！
  • memfd + SCM_RIGHTS 零落盘：agent.so 塞进匿名内存文件 memfd 跨进程传入；需要加载系统依赖库（或非 Mapper 回退模式）时，仍把 caller_addr 伪装成 libc->close 合法借用系统默认 namespace。
  • Zymbiote 极轻量 Spawn：做 -f 冷启动时不再往 zygote/usap 注入完整 agent，而是直接 SIGSTOP 补丁 android.os.Process.setArgV0()。

03 / Line-by-Line Source Walkthrough

逐行源码拆解（frida-core @ 075600d9 · Frida 17.27.5）

下面所有代码片段与行号均直接核验自 Frida 17.27.5 对应的 frida/frida-core @ 075600d9 提交。每一段先交代“上一棒怎么交接进来”，再精读关键行，最后指向下一棒。

3.1 入口接缝：perform_attach_to() 与 memfd 备弹

电脑端发来 attach(pid) 后，手机上的 frida-server 进入 linux-host-session.vala 的 perform_attach_to()：指定入口符号 "frida_agent_main" 并设置 AgentFeatures.CONTROL_CHANNEL，把内嵌的 agent 资源交给 Linjector，随后立刻取回与 agent 直连的 IOStream 交给上层建立 P2P D-Bus 会话。

3.2 ptrace 劫持与 RemoteCall：假返回地址 0x320

LinuxHelperBackend 打开 InjectSession（继承 SeizeSession）：Linux 3.4+ 优先用 PTRACE_SEIZE + PTRACE_INTERRUPT 静默接管并暂停目标线程，通过 PTRACE_GETREGSET 备份完整寄存器 saved_registers。之后每一次在目标进程里远程调函数，都由 RemoteCall.execute() 完成：

  • 按 ARM64 调用约定将参数写入 x0..x5，把 PC 改成目标函数地址，把返回地址 LR (x30) 设为故意触发 SIGSEGV 的 DUMMY_RETURN_ADDRESS = 0x320；
  • 放行目标线程执行，等函数 RET 跳去 0x320 触发 SIGSEGV 时被 ptrace 精准拦回，核对 PC == 0x320 后从 x0 读出返回值，并立即写回 saved_registers 还原现场。

怎么先在目标进程里开辟第一块 RWX 内存？（bootstrap L1092–1150）

① 常规快路径：目标与 frida-server 共用同一份系统 libc.so 时，直接按基址 + 偏移算出 remote_mmap，一次 RemoteCall 调 mmap(RWX) 拿到 allocation_base。

② 兜底冷路径（ProcessCodeSwapScope，L2417）：若目标与服务端不是同一份 libc，则冻结其他全部线程，借用目标进程某段可执行页临时覆盖写入 bootstrapper，让它自己发系统调用 mmap 申请 RWX 页后再原样恢复原代码页。

3.3 阶段一 bootstrapper.c：无 libc 探测符号并建匿名 ctrlfds

拿到 allocation_base 后，frida-server 写入预编译的无 libc 载荷 bootstrapper-arm64.bin 并用 RemoteCall 执行 frida_bootstrap(ctx)：

  1. 读 /proc/self/auxv 与动态链接器的 r_debug 链表，找到目标进程的 linker64 和 libc.so 基址；
  2. 扫描 ELF 导出表填满 FridaLibcApi（包含 mmap、munmap、pthread_create、recvmsg、send 以及 Android linker 的 __loader_dlopen / __dl__Z8__dlopenPKciPKv）；
  3. 若内核支持 pidfd_getfd（Linux 5.6+），直接在目标进程内 socketpair() 建一对 ctrlfds[0..1]——返回后，frida-server 在 establish_connection()（L1281–1320）里用 pidfd_open + pidfd_getfd(ctrlfds[0]) 隔空把对端 FD 复制回自己进程，连 abstract socket 名称都不留！

3.4 阶段二 loader.c：秒退主线程 + Frida 17 默认自映射（HAVE_MAPPER）双路径

进入 InjectSession.inject()（L915–944），服务端把 loader-arm64.bin 与上下文覆盖写进 allocation_base。注意第 933–935 行：因为在 meson.build:1019 中 Linux/Android 默认定义了 HAVE_MAPPER，服务端会直接置位 loader_ctx.agent_mapped = 1！

回退路径（当关闭 -Dmapper=disabled 时，loader.c:120-151）的 17.27.5 新细节：如果构建时关闭了 Mapper，loader 仍会走 dlopen 分支——同样通过 pretend_caller_addr = libc->close 绕过 Android Linker Namespace，但注意 17.27.5 第 136 行把路径从旧版的 /proc/self/fd/%d 改成了 /proc/%d/fd/%d（frida_getpid()）！源码注释解释得很精辟：当目标 App 同时挂着调试器时，调试器收到 linker 的库加载事件后会从外部读该路径；写 /proc/self 会误读成调试器自己的 FD 表导致线程卡死在 dlopen() 里，换成明确 PID 就能内外解析一致。

05 / Attach vs Zymbiote Spawn

Frida 17 的另一大进化：-f（Spawn）如何用 Zymbiote 取代 Zygote 注入？

在 Android 上，App 全是由 zygote / zygote64（以及 Android 10+ 的 usap32 / usap64 进程池、甚至 com.android.chrome_zygote）fork 出来的。Frida 16 时代做 -f Spawn 需要往 Zygote 注入庞大的 frida-agent.so；而 Frida 17.27.5 彻底改用极轻量的 Zymbiote（zymbiote-arm64.elf）！

它的工作流非常干净：当 frida -U -f com.example.demo 触发 RoboLauncher.spawn() 时，SystemServerAgent 先停止并重新拉起目标包；一旦 Zygote fork 出新子进程并调用 android.os.Process.setArgV0("com.example.demo")，被替换的槽位就会触发 Zymbiote 连回 frida-server（ZymbioteConnection 发送 Hello），在业务代码运行前原地暂停，等 CLI 对这个新 PID 走完前文的 perform_attach_to() 并装好脚本后，再发送 resume 放行！

对比维度 Attach 模式（frida -U -N 包名） Spawn 模式（frida -U -f 包名）
前置动作 App 必须已在运行，直接按包名找到现有 PID 向 zygote/usap/chrome_zygote 植入极小 Zymbiote 补丁，再借 system_server 重启 App
对其他 App 的影响 零影响 相比 Frida 16 不再往 Zygote 注入庞大 frida-agent.so，非目标 App 收到 resume 即直接继续
脚本介入时机 随时附加，但错过 JNI_OnLoad / 早期初始化 在 setArgV0() 时即挂起，早于 Application.onCreate() 与业务 .so 加载
载入 frida-agent.so perform_attach_to() → 本文两阶段自映射注入 捕获挂起 PID 后，同样走 perform_attach_to() 两阶段自映射注入，装完脚本再放行

06 / Forensic Footprint

原理反推：Frida 17.27.5 注入后，进程里还留有哪些痕迹？

启用默认 HAVE_MAPPER 自映射后，痕迹相比老版本发生了明显变化——从 linker 链表里消失了，但内核视图里仍有迹可循：

1. Linker soinfo 隐身，但 /proc/pid/maps 仍有映射

因为 frida_map_agent() 绕过了 dlopen(agent.so)，通过 dl_iterate_phdr 或 Android linker 内部 soinfo 链表找不到 frida-agent.so；但在内核 /proc/pid/maps 中，阶段一的匿名 rwxp 页、MAP_FIXED 映射的 /memfd:... (deleted) 代码段与匿名可写数据段依然存在。

2. /proc/pid/task/*/comm 里的后台线程

阶段二拉起 worker 线程，进入 frida_agent_main() 后 GLib 和 GumJS 仍会创建 gmain、gdbus、gum-js-loop、pool-frida 等线程；Gum.Cloak 只过滤 Frida 自身的 API 枚举，外部直接遍历 /proc/pid/task 依然可见。

3. TracerPid 短暂窗口与匿名 Unix Socket

PTRACE_SEIZE 到 DETACH 的几毫秒内 TracerPid 非 0；进程内新增的 ctrlfd / agent_ctrlfd 在 /proc/pid/fd 中体现为匿名 Unix Socket（Linux 5.6+ 因使用 pidfd_getfd，不会在 /proc/net/unix 留下 @/frida-* 名称）。

4. frida-server 27042 端口与 Zymbiote 补丁

设备端常驻进程默认监听 27042 并响应 D-Bus AUTH（详见 D-Bus 专题）；若使用过 -f Spawn，Zygote 内存里的 setArgV0 槽位和 Zymbiote 载荷也会伴随进程生命周期存在。
