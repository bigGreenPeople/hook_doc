Frida 里的 D-Bus 到底是什么？

看 Frida Android 调用链时，最容易让人卡壳的一个名词就是 D-Bus：Windows 上没有它，Android 里也没有 Linux 桌面的 dbus-daemon，那电脑和手机之间到底是怎么“建立 D-Bus 连接”的？这篇补充笔记专门把这个概念讲透。

01 / Breaking the Misconception

一句话先搞懂：它在这里是一种“点对点 RPC 协议”

不要被名字里的 “Bus（总线）” 误导。在 Frida 里，D-Bus 不是操作系统里的某个服务进程，而是两端直接讲的一种二进制 RPC 通信协议——你可以把它类比成 gRPC 或 带类型定义的二进制 JSON-RPC。

传统 Linux 桌面里的 D-Bus（总线模式）

通常有一个常驻的中央守护进程 dbus-daemon（System Bus / Session Bus），桌面程序都连到这个中转站，按服务名互相发消息。

  • 强依赖系统预装的 dbus-daemon
  • 常见于 Ubuntu / GNOME / systemd 等桌面 Linux
  • Windows 和 Android 默认都没有这东西

Frida 用的 D-Bus（点对点 P2P 模式）

Frida 根本不需要 dbus-daemon！它直接把 GLib 的 GDBus 库静态编译进自己的程序里，在一条普通字节流上跑 Peer-to-Peer（P2P）D-Bus 协议。

  • 只要两端之间有一条双向流（ADB 通道 / TCP / Unix Socket）就能跑
  • Windows、macOS、Linux、Android、iOS 全平台通用
  • 完全不依赖目标系统是否装了 D-Bus 服务

一句话记住：ADB 负责把字节从电脑的 USB 线搬到手机端口（相当于“修路”）；D-Bus 规定了在这条路上来回跑的数据包长什么样、怎么调用对方函数、怎么把事件推回来（相当于“路上的交通规则和语言”）。

02 / Why D-Bus

为什么 Frida 选中了 D-Bus，而不是 HTTP 或自造协议？

看完 frida-core 的技术栈，选择 D-Bus 其实是水到渠成的工程决定：

REASON 01

Vala + GLib 原生支持

frida-core 主体用 Vala 编写（构建在 GLib/GIO 之上）。Vala 语言层面直接内置 [DBus] 注解，声明一个接口就能自动生成客户端代理与服务端分发代码，几乎零样板代码。

REASON 02

天然支持双向通信

Frida 不仅要“电脑调手机”（RPC 方法调用），还要随时接收 App 里 console.log() / send() 吐出来的异步日志（Signal / 回调消息）。D-Bus 天生是全双工的。

REASON 03

传输层完全解耦

GLib.DBusConnection 只认抽象的 IOStream。换 ADB、换远程 TCP、换本机 Unix Socket/Pipe，上层的 HostSession 和 AgentSession 接口代码一行都不用改。

顺便解开一个实战踩坑：为什么电脑 frida 和手机 frida-server 版本不一致常会报错？
就是因为 D-Bus 接口名里带着协议版本号（如 re.frida.HostSession16 / HostSession17）。大版本不匹配时，两端的接口契约或方法签名对不上，D-Bus 调用就会直接失败。

03 / Where It Lives in Frida

在 Frida Android 链路里，D-Bus 跑在哪两段？

很多人只注意到“电脑连手机”这段用了 D-Bus，其实整个三进程链路里，跨机器和跨进程两段控制通道都是用 D-Bus 讲同一套语言：

进程 A：电脑 frida frida-tools + _frida.pyd
（含电脑端 Core）
第 1 段 P2P D-Bus（跨机器） 底层通道：ADB 转发 → 手机 127.0.0.1:27042
主要接口：HostSession + 中继后的 AgentSession
进程 B：frida-server Android 独立高权限 PID
ControlService 监听并中继
第 2 段 P2P D-Bus（本机跨进程） 底层通道：本机 Socket / Pipe
主要接口：AgentSession 与 AgentMessageSink
进程 C：目标 App 被注入的 frida-agent.so
（含 Gum + GumJS）

提示：当你在电脑上调用 script.load() 时，请求经第 1 段 D-Bus 到达 frida-server，再由服务端通过第 2 段 D-Bus 转发给目标 App 内的 agent.so；console.log() 则沿这两段反向传回。

Frida 最核心的两个 D-Bus 对象

接口名称 常见对象路径 提供方（谁实现） 主要管什么事
HostSession /re/frida/HostSession 手机端 frida-server（ControlService） 设备级操作：查系统信息、枚举运行中进程与应用（-N 找包名靠它）、spawn、attach(pid)、kill。
AgentSession /re/frida/AgentSession/... 目标 App 内的 frida-agent.so（经 server 中继给电脑） 单进程脚本操作：create_script（把 hook.js 送进去）、load_script、destroy_script、post_messages，并配对 AgentMessageSink 把 console.log / send() 推回电脑。
