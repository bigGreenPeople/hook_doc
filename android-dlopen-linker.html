01 / Static (.a) vs Shared (.so)

从动手开始：什么是静态库和动态库？怎么亲手做一个？

不管后面的 ELF、重定位、dlopen 听起来多复杂，源头其实非常朴素：我们写了一段可复用的 C 函数，想打包给别的程序用——到底是在“编译时直接拷贝进去”，还是“等程序跑起来时再加载进来”？这就是静态库和动态库的根本分野。

先准备一个最简单的 3 行源码文件 math_util.c（加上头文件 math_util.h）和调用方 main.c：

STATIC LIBRARY · 静态库（.a）

什么是静态库？—— 编译期直接“复制粘贴”

静态库（Android / Linux 后缀 .a，Archive 归档包）本质上就是把一堆编译好的 .o 目标文件打成一个包（类似不压缩的 .zip）。当你链接它时，链接器直接把用到的函数机器码完整拷贝进你的最终程序里；程序生成后，哪怕把 .a 文件删掉也照常运行！

SHARED LIBRARY · 动态库（.so）

什么是动态库？—— 运行期才“按需挂载”

动态库（Android / Linux 后缀 .so，Shared Object 共享对象）在编译链接时不会把代码拷进调用方，只在调用方里记一条账（DT_NEEDED: libmath_util.so）；等程序真正跑起来时，再由系统的动态链接器（linker64）或代码里的 dlopen() 把 .so 映射进内存并把函数地址接上！

一张表分清静态库 .a vs 动态库 .so

对比维度 静态库（.a） 动态库（.so）
文件本质 多个 .o 目标文件的 ar 打包归档 完整的 ELF 共享对象（ET_DYN）
链接发生时机 编译链接期（把机器码直接拷贝合并，地址一次性算死） 程序运行期（启动时由 linker64 自动加载，或运行中调 dlopen()）
运行时依赖文件吗 不依赖，最终产物自包含（体积较大） 依赖，磁盘或内存里必须能找到对应的 .so（多进程可共享同一份只读代码页）
在 Frida 里的真实案例 libfrida-gum.a / libsepol.a 被静态编进 frida-agent.so 和 frida-server，所以手机里看不到独立文件 frida-agent.so 本身就是一个动态库，同时它运行期又依赖系统的 libc.so、liblog.so 等动态库

02 / Meet ELF From Scratch

先认识 ELF：Android 里的 .so 文件到底长什么样？

ELF（Executable and Linkable Format）是 Linux 与 Android 统一的二进制文件格式，地位就像 Windows 里的 PE 格式（.exe / .dll）。Android 上的 frida-server、/system/bin/linker64 以及每一个 .so 动态库都是 ELF 文件——拿十六进制编辑器打开，开头前 4 个字节永远是魔数 7F 45 4C 46（即 \x7fELF）。

2.2 彻底看懂 PT_LOAD：dlopen 映射内存的“施工单”

Program Header Table 里通常有 7～10 条 Elf64_Phdr 记录，每条都有一个 p_type 类型字段。其中只有标记为 PT_LOAD（枚举值 = 1，意为 Program Type: Loadable）的条目，才会真正被 mmap 搬进内存！其余常见类型大多只是“指路牌”：

  • PT_LOAD（通常 2～4 条）：真正要映射进进程内存的段。为什么拆成 3～4 条而不是合一起用 1 条？因为现代 CPU 控制权限的最小单位是一整页内存（4KB / 16KB），且安全规范要求 W^X（可写不可执行、可执行不可写），所以链接器把只读元数据（R--）、机器码（R-X）、RELRO 表（RW- → R--）、可写数据（RW-）分别打成独立的 PT_LOAD。
  • PT_DYNAMIC（1 条）：指路牌（本身数据已包在某个 PT_LOAD 内），告诉 dlopen 动态链接总表（.dynamic）在哪个虚拟地址。
  • PT_GNU_RELRO（1 条）：指路牌，告诉 dlopen 重定位填完 .got 后，把哪一段地址用 mprotect 锁死成只读。
  • PT_GNU_STACK / PT_NOTE：辅助属性标记（声明栈不可执行、记录构建信息等）。

2.3 正文里常见的 7 个核心零件速查表（后面反复出现）

名字 通俗理解 谁会用到它
.text / .rodata 编译出来的 ARM64 机器指令 / 只读常量（如字符串字面量） CPU 直接取指执行 / 读取（R-X 与 R--）
.data / .bss .data 存有初始值的全局变量；.bss 存未初始化（默认为 0）的全局变量，在磁盘里占 0 字节 运行期读写（RW-），.bss 由 dlopen 在内存展开并清零
.dynamic（PT_DYNAMIC） 动态链接总索引表：里面一条条记着 DT_NEEDED（依赖库名）、符号表地址、重定位表地址、构造函数地址 dlopen 进内存后第一个解析的“总控说明书”
.dynsym & .dynstr 动态符号表 & 字符串表：记录本库导出哪些函数名（供别人 dlsym）以及导入哪些外部函数名 dlopen 重定位查外部符号 + 外部调 dlsym()
.rela.dyn & .rela.plt 重定位“填空清单”：一条条列明“内存哪个偏移处需要填库内新地址或外部函数地址” dlopen 步骤 5 遍历执行填空
.got & .plt .got（Global Offset Table）是存放真实函数/变量地址的指针槽数组；.plt 是跳转桩代码，负责从 .got 取出地址跳过去 实现 -fPIC 地址无关调用的核心跳板
.init_array 函数指针数组：存放 C++ 全局对象构造函数以及 __attribute__((constructor)) 标记的初始化函数 dlopen 全部链接完毕后自动逐个执行

2.4 别搞混：.dynamic 和 .dynsym / .dynstr / .rela.plt 怎么协作？

初学者常误以为 .dynamic 里直接写满了本库用到的每一个外部函数名。其实 .dynamic 只是一张 Key-Value 总索引表：它直接记录“依赖哪些外部 .so 库名（DT_NEEDED）”，然后用指针分别指向真正存函数名和填空槽位的另外三张表：

经典冷知识（ELF 与 Windows DLL 的重要区别 · LD_PRELOAD 劫持原理）：
在 Windows PE（.dll）里，导入表会明确写死“去 kernel32.dll 找 CreateFileW”；但在 Linux / Android 的 ELF 里，DT_NEEDED（依赖库清单）和 .dynsym（外部函数清单）是平级分开的，并没有把每个外部函数死绑到某一个具体 .so 上！运行期 dlopen 查 __android_log_print 时，会沿着已加载的依赖库顺序挨个查，谁先导出同名符号就用谁的——这正是 Linux/Android 上 LD_PRELOAD 能够抢先劫持系统函数的底层原因。

03 / From Build Time to Runtime

前置桥梁：编译链接、ASLR 与 dlopen 的交接

认识了 ELF 的零件后，就能看懂为什么 .so 里偏偏要有 .got 和重定位表：编译期（电脑上 clang + lld）负责出一张“留好空白格的试卷 + 填空说明书”，运行期 dlopen 负责把真实内存地址填进去。而逼出这套机制的幕后推手，就是 ASLR。

先扫清一个核心名词：ASLR 是什么？（Address Space Layout Randomization，地址空间布局随机化）

它是 Android / Linux / iOS / Windows 默认开启的内核安全机制：为了防止黑客利用缓冲区溢出直接跳去固定地址的 system()，内核在每次启动进程或 dlopen 加载 .so 时，都会随机挑选一个内存加载基址（比如这次 libdemo.so 落在 0x7b40_0000，下次重启变成 0x7e91_0000）。

这也解释了两件大事：① 编译期根本不可能提前写死绝对内存地址，只能把“最终基址 load_bias”留给运行期 dlopen；② Frida 写 Native Hook 时总要写 Module.findBaseAddress("libxxx.so").add(0x1234)（IDA 看到的是相对偏移，真机运行必须加上本次随机基址）。（注：Android 上所有 App 都由同一个 zygote 进程 fork 出来，因此 zygote 里早已加载好的系统库在同一次开机周期内基址往往相同，重启手机才会重新随机。）

编译 / 静态链接期干的事 留在 .so 里的结构 运行期 dlopen() 接手干的事
1. 开启 -fPIC 地址无关代码 .got / .plt（初始为空或占位地址） 只读代码段（.text）一字节都不改，只需把真实地址写进可写的 .got 槽位
2. 登记编译参数里的 -llog -lm PT_DYNAMIC → DT_NEEDED 按依赖名递归加载 liblog.so、libm.so 等外部库
3. 列出所有待修正的地址位置 .rela.dyn / .rela.plt（重定位表） 逐条计算 load_bias + addend 或外部符号地址，回填到目标槽位
4. 按权限合并段 & 汇总导出/构造 PT_LOAD、.dynsym、.init_array 按 PT_LOAD 做 mmap，用 .dynsym 支撑 dlsym，最后执行 .init_array

回到第 01 章的疑问：制作 .so 时，为什么必须加上 -fPIC？
如果不加 -fPIC，编译器会在只读代码段（.text）里直接写死绝对地址，导致运行期 dlopen 被迫改写代码页（Text Relocation / DT_TEXTREL），破坏多进程共享只读代码页——Android 6.0+ 已直接禁止加载带文本重定位的 .so。加上 -fPIC 后，代码段保持纯只读，所有待修正地址全部集中到数据段的 .got 槽位里。

04 / ELF On Disk vs In Memory

ELF 双视图深度对比：磁盘上的 .so vs 加载进内存后的 .so

这是理解 dlopen、写微型 Linker、甚至做逆向内存 dump .so 时最容易踩坑的核心分水岭：一个 .so 躺在磁盘上时是“紧凑打包的”，加载进内存后会被按内存页（4KB / Android 15 为 16KB）重新展开、拉出空隙、补出 .bss，还会直接扔掉节表！

磁盘 ELF 与内存 ELF 的 5 个关键差异速查

维度 磁盘上的 .so 文件 加载进内存后的 .so
核心索引表 Program Header（Phdr）与 Section Header（Shdr）都在 只用 Phdr（特别是 PT_LOAD 与 PT_DYNAMIC）；Shdr 根本不进内存
段间距与大小 紧凑排列，省磁盘空间（按 p_offset / p_filesz） 不同权限的段必须分属不同内存页（4KB 或 Android 15 的 16KB），页边界间有对齐间隙
.bss 区域 占 0 字节，仅在 p_memsz > p_filesz 中记录大小 真实分配可写内存并全部清零（尾字节 memset + 多出整页匿名 mmap）
.got 表内容 空的 0 或指向 .plt 桩代码的初始占位值 已经被 dlopen 填满真实运行期函数/全局变量地址，并常被 RELRO 锁成只读
内存权限 磁盘文件无页级权限区分 严格拆分 R--（元数据）、R-X（代码）、RW-（数据），遵循 W^X（不同时可写可执行）

05 / Inside bionic/linker64

Android dlopen() 6 步全流程拆解

当你写下 dlopen("libdemo.so", RTLD_NOW)，libdl.so 只是一个空壳转发器，真正干活的是位于 /system/bin/linker64 里的 __loader_dlopen() → do_dlopen()。整个过程可以拆成 6 个环环相扣的步骤：

1

Android 7+ Linker Namespace 权限校验

dlfcn.cpp → linker.cpp::dlopen_ext()

Android 7.0 起引入了 Linker Namespace 隔离：防止普通 App 随便 dlopen 系统私有库（如 libart.so）。调用 dlopen() 时，libdl.so 会通过 __builtin_return_address(0) 把调用者的返回地址 caller_addr 传给 __loader_dlopen(name, flags, caller_addr)。

linker64 查 caller_addr 落在哪个 soinfo 里，进而确定你属于 classloader-namespace（App 沙箱命名空间，只能访问 NDK 公开白名单系统库）还是 default（系统命名空间）。

呼应 Frida 注入原理：这就是为什么 《Frida 17 注入原理》动作 6 里，匿名 RWX 页里的 loader.c 调 __loader_dlopen 时，必须把第 3 个参数 caller_addr 伪装成 libc->close 地址——因为匿名页不属于任何 soinfo，不伪装就会立刻被 Namespace 拦截；伪装成 libc.so 里的地址就合法借用了系统 default 命名空间！

2

查全局 solist 缓存与打开文件

linker.cpp::find_libraries() → load_library()

先在当前 Namespace 已加载的 soinfo 列表中查找同名库（或同一 inode 的文件）：

  • 如果已经加载过：直接把 ref_count++ 并返回已有句柄，不会重复映射内存、也不会再次执行 .init_array（这也是 Frida 预加载 liblog.so 时几乎零开销的原因）。
  • 如果尚未加载：按当前 Namespace 的搜索路径（如 App 的 lib/arm64、/system/lib64）找到文件并 open() 拿到 FD（若是 Android APK 里未解压的 .so，还支持直接从 ZIP 偏移 p_offset 映射）。
3

ElfReader::Load()：预留连续地址并映射 PT_LOAD 段

linker_phdr.cpp::ElfReader::Load()

这是“磁盘 ELF 变成内存 ELF”的物理动作，一共三小步：

  1. 算总跨度并 ReserveAddressSpace()：遍历所有 PT_LOAD 算出最低虚拟地址 min_vaddr 和最高虚拟地址 max_vaddr，用 mmap(NULL, max_vaddr - min_vaddr, PROT_NONE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0) 一次性向内核圈出一整块连续虚拟地址，从而算出 load_bias = base - min_vaddr（保证各段之间的相对距离与编译期完全一致，PC 相对寻址指令才不会错！）。
  2. 逐段 LoadSegments()：对每个 PT_LOAD，用 mmap(seg_page_start, ..., MAP_FIXED, fd, file_page_start) 把磁盘内容精准贴到预留区间内的对应位置，按 PF_R/W/X 设置权限；遇到 p_memsz > p_filesz 时把 .bss 尾部清零并补齐匿名零页。
  3. FindPhdr()：记录内存里的 Program Header 地址，为后面解析 PT_DYNAMIC 做准备。
4

解析 PT_DYNAMIC 并递归加载 DT_NEEDED 依赖树

linker.cpp::soinfo::prelink_image()

prelink_image() 遍历内存中的 PT_DYNAMIC 数组，把后续重定位需要的表地址全提出来放进 soinfo 结构体（DT_SYMTAB 符号表、DT_STRTAB 字符串表、DT_GNU_HASH 哈希表、DT_RELA / DT_JMPREL 重定位表、DT_INIT_ARRAY 构造函数表）。

同时收集所有 DT_NEEDED 依赖库名（例如 liblog.so、libc.so），以广度优先顺序把整棵依赖树先全部完成步骤 2 和步骤 3，确保接下来查外部符号时，所有依赖库都已经在内存里就位了。

5

重定位（Relocation）“填满 GOT 表” + GNU_RELRO 锁只读

linker_relocate.cpp::soinfo::relocate()

这是动态链接最核心的“填空”环节。在 ARM64（AArch64）上，每条重定位记录 Elf64_Rela 只有 3 个字段：要改哪里的偏移 r_offset、重定位类型与符号索引 r_info、加数 r_addend。最常见的 3 种填空公式如下：

紧接着执行 ApplyGnuRelro()：全部重定位填完后，linker64 立刻调用 mprotect(relro_start, relro_size, PROT_READ) 把 PT_GNU_RELRO 覆盖的 .got、.dynamic、.init_array 全部锁成只读，防止运行期被内存漏洞随意改写 GOT 表！

6

登记全局 soinfo 账本 + 按依赖顺序执行 .init_array

linker.cpp::soinfo::call_constructors()

链接完成后，新创建的 soinfo 结构体已经稳稳挂在 linker64 的全局链表 solist 中（记录着文件名、load_bias、phdr、符号表指针等全部信息——这就是风控调用 dl_iterate_phdr() 时遍历的账本！）。

最后，call_constructors() 遵循“先依赖库、后自己”的顺序，依次执行 DT_INIT 和 DT_INIT_ARRAY 里的每一个初始化函数（C++ 全局对象构造、__attribute__((constructor)) 函数都在这里运行）。全部跑完后，dlopen() 把句柄返回给调用方！

07 / Security Perspective & Next

风控视角回看：为什么标准 dlopen 藏不住注入的 .so？

走完上面 6 步，就能一眼看出安全风控/反注入SDK为什么能轻松抓出通过系统 dlopen() 注入的 .so——几乎每一步都留下了公开可查的痕迹：

TRACE 01 · soinfo 账本

dl_iterate_phdr() 一秒查全表

标准 dlopen 第 6 步会把新库挂进 linker64 的全局 solist。App 只要调用标准 C 函数 dl_iterate_phdr()，就能直接拿到进程里所有已登记 .so 的名字、基址和 Program Header。

TRACE 02 · /proc/self/maps 文件路径

文件映射自带路径名

ElfReader 对文件 FD 执行 mmap 时，Linux 内核会在 /proc/self/maps 里清清楚楚标出文件路径（如 /data/local/tmp/libevil.so 或 /memfd:...）。

TRACE 03 · Linker Namespace 拦截

跨命名空间调用直接拒载

Android 7+ 限制普通 App 的 classloader-namespace 不能直接 dlopen 非公开系统库或外部目录，逼得注入器必须伪造 caller_addr（如 libc->close）。

TRACE 04 · 死锁与调试器通知

全局锁 + r_debug 通知

linker64 内部维护全局互斥锁 g_dl_mutex，在 ptrace 暂停期间直调极易死锁；同时每次 dlopen 还会触发 rtld_db_dlactivity() 通知外部监控。

把知识串成闭环：正因为 dlopen() 本质上就是「① 映射 PT_LOAD + 清 .bss → ② 加载依赖 → ③ 算重定位填 GOT → ④ 登记 soinfo → ⑤ 调 .init_array」，如果我们自己把 ①②③⑤ 写了、唯独跳过第 ④ 步“登记 soinfo”，我们就亲手造出了一个像 Frida 17 HAVE_MAPPER 一样的微型无痕 Linker！
