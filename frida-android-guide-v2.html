Frida Android 入门与源码仓库拆解

研究 Frida 在 Android 上的工作原理，最稳妥的第一步不是直接啃底层注入和 ART 内存布局，而是先亲手跑通一个最简单的 Java 方法 Hook，再带着疑问打开 Frida 的 Git 仓库：把里面拆出来的几个子项目——用什么语言写、编译产出是什么、原本干什么用、最终怎么被加载在哪里运行——彻底盘清楚。

01 / Hands-On First

Frida 基本使用：写一个最简单的 Java 方法 Hook

动手之前先不管 frida-core、GumJS 这些术语，我们只做一件事：在 Android 上拦截一个运行中测试 App 的 Activity.onResume()，每次界面回到前台就在电脑终端打印一行日志。

1.1 运行前的两端准备

电脑端（Windows）：安装命令行工具

安装 frida-tools（会自动连带安装 Python 绑定包 frida），装完后终端就有 frida、frida-ps 等命令了。

pip install frida-tools==12.5.0 frida==16.4.7

手机端（Android，root）：启动 frida-server

从发布页下载与手机 CPU 架构（如 arm64）和电脑端版本一致的 frida-server，推到手机里以后台高权限运行。

adb push frida-server /data/local/tmp/
adb shell "su -c 'chmod +x /data/local/tmp/frida-server && /data/local/tmp/frida-server &'"

02 / Exploring the Git Repository

查看 Frida 的 Git 项目：原来是由多个子项目拼出来的

直接打开 GitHub 上的主仓库 frida/frida，第一眼很容易愣住：根目录几乎没有业务代码，全都是构建脚本和子模块配置文件。

frida/frida @ a93582c 根目录结构 
frida/
├── .gitmodules          # 锁定每个子项目的仓库地址与提交
├── configure(.bat)      # 初始化构建环境
├── Makefile / meson.build # Meson 总控构建入口与依赖编排
├── meson.options        # 编译开关（JS 引擎、组件裁剪等）
├── releng/              # 跨平台工具链与打包脚本（子模块）
├── tools/               # ensure-submodules.py 等辅助脚本
├── .github/ & .cirrus.yml # 多平台 CI 编译发布流水线
└── subprojects/         # 真正写核心代码的各个独立子项目
    ├── frida-tools/     # ★ 命令行工具（frida / frida-ps）
    ├── frida-python/    # ★ Python 绑定与原生扩展
    ├── frida-core/      # ★ 核心控制、服务端、注入与 agent
    ├── frida-gum/       # ★ 底层插桩引擎与 GumJS 运行时
    └── frida-node / frida-swift / frida-clr / ...
                         #   其他语言绑定（本例不涉及）
主仓库 frida/frida 本身不是业务代码库

它是一个总控构建与发布编排仓库：用 .gitmodules 把分散在多个独立仓库里的子项目拉到 subprojects/ 下，再由 Meson + releng/ 统一编排交叉编译和打包。

我们刚才那次 Hook，只涉及 4+1 个核心项目

subprojects/ 里有很多其他语言绑定（Node.js、Swift、C#/.NET、QML 等）。在「Windows 命令行 → Android Java Hook」这条路径上，真正出场的只有主仓库里的 4 个核心子项目，外加专门负责 Android ART 的 frida-java-bridge。

先把一个常见困惑提前拆掉：为什么文件数量比项目少？

在 Frida 16.4.7 默认构建里，大量底层库在编译期就被静态链接合并了——比如电脑上看不到单独的 frida-core.dll，手机 App 里也看不到单独的 libfrida-gum.so。下一节拆解每个子项目时，我们会专门标清楚“谁合并进了谁”。

主仓库锚点： frida/frida · .gitmodules · subprojects/ · meson.build · releng

03 / Subprojects Breakdown

逐个拆解子项目：语言、产出、职责与运行位置

下面按「从你敲命令的电脑，一路深入到手机目标 App 内部」的顺序，逐个拆解这 5 个核心项目。每个项目都严格回答同样的 4 个问题：用了什么语言 → 编译产出有什么 → 原本是干什么的 → 最终怎么被加载、运行在哪里。

1

frida-tools

命令行前端套件
Python 运行于：电脑 CLI 进程
① 使用语言

Python 为主；内部也附带少量用于交互式 REPL / frida-trace 的 JavaScript 辅助脚本。

④ 怎么被加载、运行在哪里

通过 pip install frida-tools 安装到电脑 Python 环境。你在终端敲下 frida 时，操作系统直接启动一个电脑端 Python 进程，入口为 frida_tools.repl:main，它只负责“前端发令与展示”，永远不碰手机内存。

② 编译 / 打包产出 & ③ 原本是干什么的
  • frida-tools Python 包 & CLI 命令入口 frida / frida-ps / frida-trace 等
    把命令行参数（-U、-N、-l）解析成对 Python API 的调用：先查设备上的应用列表把包名换成 PID，再读入本地 hook.js 文本下发，并把手机回传的 console.log 打印到终端。
  • 内置辅助 JS 脚本 如 REPL / trace 模板
    当你使用交互式命令行补全或 frida-trace 时，CLI 会把这些辅助脚本发往目标 App 内的 JS 引擎执行。
它在第 1 节 Demo 里的角色：就是你敲下的 frida ... 命令本身。
pyproject.toml 命令入口 L61 application.py L613
2

frida-python

Python 绑定与 C 扩展桥
Python + C 运行于：电脑 CLI 进程
① 使用语言

上层是 Python 面向对象包装，下层是 C 语言编写的 CPython 原生扩展（extension.c）。

④ 怎么被加载、运行在哪里

随 pip install frida 安装在电脑上。当 frida-tools（或你自己的控制脚本）执行 import frida 时，Python 解释器把 _frida.pyd 作为原生扩展动态库加载进同一个电脑端 Python 进程里运行。

② 编译产出 & ③ 原本是干什么的
  • frida Python 包（如 frida/core.py）
    向 Python 世界暴露 Device、Session、Script 等易用对象；无论命令行还是自己写自动化脚本，都通过这层调底层。
  • _frida.pyd（Windows，Linux/macOS 为 _frida*.so） 内含静态链接的电脑端 frida-core
    本质是 CPython 可直接 import 的 DLL。它把 device.attach(pid) 等 Python 方法转调到静态链接在自己体内的 frida-core C 函数（如 frida_device_attach_sync()），并把底层异步收到的日志回调抛回 Python。
它在第 1 节 Demo 里的角色：连接 Python CLI 与底层 C/Vala 核心的“跨语言桥梁”。
frida/meson.build core.py L1058 extension.c L2854
3

frida-core

跨端通信、进程注入与会话中枢
Vala + C/C++ 电脑进程 frida-server 进程 目标 App 进程
① 使用语言

主体用 Vala 编写（构建时先由 valac 转译为标准 C 代码，再由 C 编译器编译为各平台原生机器码），底层平台注入器与系统适配部分用 C / C++ 和少量汇编。

④ 怎么被加载、运行在哪里

这是唯一一个产物横跨全部三个进程的仓库：它的 Core 库一边被静态编进电脑端 _frida.pyd，一边编成手机上独立运行的 frida-server；当需要 Hook 某个 App 时，再由 frida-server 把它编出来的 frida-agent.so 注入到目标 App 进程里。

② 编译产出 & ③ 原本是干什么的（一共编出 4 类核心产物）
  • 1. Core 内部原生库（及官方 devkit 静态库） 静态链接进 _frida.pyd 与 frida-server
    双端复用的核心逻辑：在电脑端负责通过 ADB 找 Android 设备并建立 D-Bus 通信（droidy-host-session.vala）；在手机端负责接收指令、枚举应用与调度注入（linux-host-session.vala）。
  • 2. frida-server（Android 原生 ELF 可执行文件） Android 独立 PID
    手动推到手机上以高权限启动的常驻守护程序。监听来自电脑的 D-Bus 请求，按包名找 PID、调用注入器把 agent.so 送进目标 App，并在电脑与 App 之间中继消息。
  • 3. frida-agent.so（Android 共享库） 注入到目标 App PID 内含静态链接的 Gum + GumJS
    真正进入目标 App 地址空间的“卧底组件”。由 frida-server 在附加时按需加载进 App，负责与服务端建立控制通道、接收 hook.js 源码、管理脚本生命周期并上报日志。（实际发布时会被打包嵌在 frida-server 内部，运行时按需释放/注入。）
  • 4. frida-gadget.so（Android 共享库） 本 Demo 未用到
    免 root / 免 frida-server 模式的替代产物：直接打包进自有测试 App，由 App 自己 System.loadLibrary() 加载并在进程内拉起 Frida 服务。
它在第 1 节 Demo 里的角色：同时包办了“电脑发请求”、“手机当服务端注入”、“App 内收脚本”三段脏活累活。
meson.build server 构建 agent 构建 gadget 构建
4

frida-gum

底层二进制插桩引擎 + JS 运行时
C / C++ (+ QuickJS/V8) 运行于：目标 App 进程
① 使用语言

C / C++ 编写跨架构底层逻辑（支持 ARM64 / ARM / x86_64），脚本运行时层集成 QuickJS（默认）或 V8 引擎，并用 JS 编写部分运行时内置模块（如 console.js）。

④ 怎么被加载、运行在哪里

在 Frida 16.4.7 默认构建中，它不会以独立的 libfrida-gum.so 出现在手机里，而是直接静态链接进 frida-agent.so。因此只要 agent.so 被注入目标 App，Gum 和 GumJS 就随之加载并运行在目标 App 进程内部。

② 编译产出 & ③ 原本是干什么的
  • Gum 原生插桩库 静态链接进 frida-agent.so
    Frida 最底层的“手术刀”：提供 Native 函数拦截（Interceptor）、指令级追踪（Stalker）、进程内存读写、模块与符号解析等 C API。即便做 Java Hook，底层读写 ART 内存和查符号也全靠它。
  • GumJS 脚本绑定库 静态链接进 frida-agent.so
    把 Gum 的 C 能力封装成 JS 全局对象（如 Memory、Module、Interceptor），负责在 QuickJS/V8 里真正执行你的 hook.js，并通过 runtime/console.js 把 console.log() 编码成消息交回 agent 传回电脑。
它在第 1 节 Demo 里的角色：在 App 内部直接跑起 hook.js，并提供底层原生操作能力。
gumjs/meson.build 默认静态链接配置 console.js L46
5

frida-java-bridge

Android Java / ART 桥接层（关键补充项目）
JavaScript（经 Gum 调 JNI / ART） 运行于：目标 App 进程
① 使用语言

JavaScript（独立仓库位于 frida-packages/frida-java-bridge）。它本身不编成 .so，而是借助 GumJS 暴露的 NativeFunction、Memory、Interceptor 直接和进程里的 libart.so / JNI 交互。

④ 怎么被加载、运行在哪里

Frida 16.4.7：打包在 GumJS 运行时内（bindings/gumjs/runtime/java.js），脚本一启动就自动挂出全局 Java 对象，运行在目标 App 进程的 JS 引擎里。
Frida 17.0+：官方把 Bridge 拆出运行时变为独立 npm/JS 包（frida-tools CLI 默认仍预装，自建 agent 需按需引入）。

② 打包产出 & ③ 原本是干什么的
  • Java Bridge JS 运行时包（提供 Java.* API） 16.4.7 随 GumJS 打包进 agent.so
    实现第 1 节脚本里的 Java.perform()、Java.use() 和 .implementation = ...。当你给 onResume.implementation 赋值时，由它内部的 class-factory.js 和 ArtMethodMangler 在目标 App 的 ART 虚拟机上完成方法接管。
它在第 1 节 Demo 里的角色：让纯 JS 脚本能看懂 Android 的类与 ART 方法，并把 onResume() 接到你的回调。

04 / Closing the Loop

收束：回到第 1 节的 Hook，看这些产出如何各就各位

把第 3 节拆出来的全部产物按实际运行进程（PID）摆回桌面，整个 Frida 的骨架就一眼看穿了——我们第 1 节敲下的那条命令，其实是一场跨越 3 个独立进程 的接力赛。

4.1 所有产出在三个进程里的最终落位

进程 A：电脑端 frida Windows PID

由命令行启动，负责读脚本、发指令、收日志。

  • frida-tools（CLI）解析 -U -N -l hook.js 并打印终端输出
  • frida-python + _frida.pydPython 到 C 扩展的调用桥
  • 电脑端 frida-core静态链接在 _frida.pyd 内，经 ADB 建 D-Bus 连接
进程 B：手机端 frida-server Android 独立 PID

高权限常驻 ELF，负责跨机接收请求并把 agent 注入 App。

  • 设备端 frida-core（ControlService）响应枚举应用与附加（attach）请求
  • Linux/Android 注入后端按包名定位目标 PID，将 frida-agent.so 注入 App
  • 会话中继在电脑端与 App 内 agent 之间转发脚本和日志
进程 C：目标 Android App App 原有 PID

真正的 Hook 现场，所有脚本运行与 ART 方法接管都在这里发生。

  • frida-agent.so被注入 App，管理脚本加载、卸载与消息上报
  • Gum & GumJS（静态链接在 agent 内）用 QuickJS/V8 跑起 hook.js，提供底层插桩能力
  • frida-java-bridge + ART执行 Java.use() 接管 Activity.onResume()
