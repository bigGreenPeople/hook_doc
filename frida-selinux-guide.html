补充专题：Frida 如何在不关 Enforcing 的情况下热修改内核 SELinux 策略？

在 Android 逆向与安全对抗中，几乎所有 App 环境检测都会第一时间读取 getenforce 或 /sys/fs/selinux/enforce。如果用粗暴的 setenforce 0 把 SELinux 切到 Permissive（宽容模式），等于直接向目标 App 亮明“这是一台被动手脚的设备”。Frida 的做法是：全程保持 Enforcing = 1，把内核正在运行的二进制 SELinux 策略镜像读进内存，用静态编译的 libsepol 现场造出 2 个专属标签、改写 MLS 跨沙箱约束位图、注入 13 条放行规则，再原子写回内核生效。

核心伪装效果
getenforce 始终为 Enforcing
/sys/fs/selinux/enforce 保持 1（仅模拟器 u:r:shell:s0 兜底分支会闪切毫秒级即刻恢复）。
新增专属类型
frida_file 与 frida_memfd
在内核策略哈希表里动态注册 2 个新 Type，并同时挂上 file_type 与 mlstrustedobject 属性。
攻克 MLS 沙箱隔离
修补编译期 Constraint 位图
遍历所有 Class 的 MLS 约束表达式，把新 Type 补进已展开的 expr->names 位图，突破 s0:c512,c768 隔离。
最小权限打孔
13 条 AVTab 规则 + 动态 $self
通过 getcon() 自动识别 frida-server 自身域（如 su/magisk），在 te_avtab 哈希表按位或置位。
01

为什么不直接 setenforce 0？（关门禁 vs 改白名单）

我们在第二篇《进程注入原理》里看到，frida-server 要把 frida-agent.so 注入到目标 App 里，必须在目标 App 进程内部完成三件对 SELinux 来说极度敏感的操作：

  1. 分配并执行匿名 RWX 内存（execmem）：Stage 1 的 bootstrapper.bin、Stage 2 的 loader.bin 以及 Gum 的 Inline Hook 跳板（Trampoline）都需要匿名可执行内存；
  2. 跨进程接收并使用来自 frida-server 的文件描述符（fd { use } + unix_stream_socket）：通过 SCM_RIGHTS 把装有 frida-agent.so 的匿名内存文件句柄（memfd）和通信 Socket 传进目标 App；
  3. 在目标 App 里把这块 memfd 映射为可执行代码（file { open, read, write, getattr, execute, map }）：由 dlopen("/proc/self/fd/N") 加载执行。
💡 大白话类比：小区门禁保安（SELinux 内核安全模块）
零基础秒懂

把 Android 内核的 SELinux 想象成严苛的大楼门禁系统。默认情况下，普通住户（目标 App，身份标签是 untrusted_app）绝对不允许接收外来人员（frida-server，身份标签是 su 或 magisk）递过来的包裹（memfd 句柄），也不允许在自己房间里私自搭违建（execmem 可执行内存）。

做法 A：直接执行 setenforce 0 极易被风控秒杀

相当于把整栋大楼的门禁总闸直接拉掉，所有大门敞开，保安只记账不拦人（Permissive 模式）。

致命缺陷：大楼门口挂着一块全员可见的指示牌 /sys/fs/selinux/enforce。任何普通 App 不需要 Root 权限，只要调一句读取文件或执行 getenforce，看到返回值变成了 0（Permissive），立刻判定环境异常并闪退。

做法 B：Frida 的内核策略热手术 门禁总闸保持开启 (1)

相当于门禁总闸依然通电（Enforcing = 1），但偷偷走进保安室，在保安手里的《通行白名单手册》里加印了 13 行字。

精妙之处：专门给 Frida 的包裹印一个专用防伪章（frida_memfd / frida_file），并在手册里写明：“凡是盖了 frida_memfd 章的包裹，所有住户（domain）都可以正常签收并运行。”

内核留给 Root 的合法后门：/sys/fs/selinux/policy 与 /sys/fs/selinux/load

很多同学会好奇：内核里的 SELinux 策略不是在编译 ROM 时写死在 boot.img / vendor.img 的 sepolicy 文件里吗？开机之后为什么还能改？

这是因为 Linux 内核的 SELinux 子系统挂载了一个虚拟文件系统 selinuxfs（在 Android 上位于 /sys/fs/selinux）。它不仅提供了查看开关状态的 enforce 节点，还提供了两个专门供特权进程（init 或 root）读取和热重载整份策略数据库的接口：

虚拟文件节点 读写方向 内核行为与 Frida 的利用方式
/sys/fs/selinux/enforce 读 / 写 (0 或 1) 全局开关。1 = Enforcing（强制拦截），0 = Permissive（仅记录日志不拦截）。App 拥有读取权限，因此绝不能长期置为 0。
/sys/fs/selinux/policy 只读（二进制流） 当你打开并读取这个文件时，Linux 内核会将当前内存里正在生效的 policydb 状态实时序列化成一份完整的二进制策略镜像返回给用户态（lib/selinux/patch.c:71）。
/sys/fs/selinux/load 只写（二进制流） 当你把一份合法的二进制策略镜像完整写入该节点时，内核的 sel_write_load() 会在内核态反序列化新策略并原子替换旧策略表，同时自动清空 AVC 权限缓存，立即生效且无需重启（lib/selinux/patch.c:148, 211）。
02

零基础看懂一条 SELinux 规则与 Android 特有的 MLS 跨沙箱隔离

在看 lib/selinux/patch.c 的 C 代码之前，我们先用 2 分钟把 SELinux 的两条底层逻辑彻底搞懂：第一是基本规则四元组（TE 规则），第二是很多逆向工程师容易忽略、但如果不处理就会导致注入彻底失败的 Android MLS 多级安全分类隔离。

2.1 一条 SELinux 放行规则长什么样？

SELinux 的核心思想是给所有进程（主体 Subject）和所有文件/Socket/内存（客体 Object）都贴上标签（Context）。一个完整的标签有四段：用户:角色:类型:安全级别(MLS)，例如目标 App 进程是 u:r:untrusted_app:s0:c512,c768，而 Frida 创建的匿名内存文件被贴上了 u:object_r:frida_memfd:s0。其中最核心的是第三段类型（Type）。

allow  domain  frida_memfd  :  file  { open read write getattr execute map };
① Source (谁来访问)
domain（属性组：代表所有进程）
这里没有写死 untrusted_app，而是写了属性组 domain——无论是普通 App、系统 App 还是 system_server，都属于 domain。
② Target (访问什么)
frida_memfd（Frida 自创标签）
只有被 frida-server 专门用 fsetfilecon() 盖上 frida_memfd 印章的匿名内存文件才会被放行，不影响系统其他文件。
③ Class (目标的类别)
file（普通/内存文件类别）
告诉内核这条规则只针对“文件”操作生效（其他常见类别还有 dir 目录、process 进程、fd 句柄、unix_stream_socket）。
④ Permissions (允许的动作)
{ open read write getattr execute map }
在内核哈希表 te_avtab 中，每个动作对应一个 32 位整数里的 1 个 Bit（位掩码 1U << (val - 1)）。

2.2 隐藏最深的坑：为什么光加 allow 规则，App 依然读不了 s0 的文件？

如果你自己写过修改 SELinux 的工具，可能会遇到一个极其诡异的现象：明明已经在 te_avtab 里加了 allow domain frida_memfd:file { ... }，为什么目标 App 在 dlopen("/proc/self/fd/N") 时还是报 avc: denied？

答案就在标签的第四段——MLS（Multi-Level Security，多级安全类别）：

  • 在现代 Android 中，为了彻底隔离不同 App 的数据，Zygote 在孵化每个普通 App 时，都会根据它的 UID 动态分配一对独一无二的 MLS Category（类别标签），比如微信是 u:r:untrusted_app:s0:c512,c768，淘宝是 u:r:untrusted_app:s0:c513,c769。
  • 而 frida-server 是以 Root 身份在后台运行的（u:r:su:s0），它创建并打标的 memfd 或临时文件，第四段安全级别固定是 s0（不带任何 cXXX 后缀）。
  • Android 的 SELinux 策略里有一条铁律（MLS Constraint 约束表达式）：带有具体 cXXX 分类的 App 进程，在读写/执行一个 s0 对象时，除非该对象的类型拥有 mlstrustedobject（MLS 受信任客体） 属性，否则一律被 MLS 约束拦截！
🔥 源码级绝技：为什么在二进制策略里挂上 mlstrustedobject 属性还不够？（patch.c:276, 294-320）

在未编译的 .te 源码策略里，只要写一句 typeattribute frida_memfd mlstrustedobject;，编译器 checkpolicy 就会自动把 frida_memfd 写进所有 MLS 约束里。 但在已经编译好的内核二进制策略（/sys/fs/selinux/policy）中，所有 Class 的 MLS 约束表达式（constraint_expr_t）在当初编译 ROM 时就已经把属性展开成静态的 Type 位图（expr->names）了！

因此，Frida 的作者 Ole André Vadla Ravnås 在 patch.c:294-320 专门写了一个函数 frida_add_type_to_class_constraints_referencing_attribute()：遍历内核里每一个 Class 的每一条 Constraint 表达式，只要发现某个表达式当年引用过 mlstrustedobject（记录在 expr->type_names->types 中），就手动把新诞生的 frida_file 和 frida_memfd 的 type_id 补进已经展开的 expr->names 位图里！

static gboolean
frida_ensure_type (policydb_t * db, const gchar * type_name, const gchar * attr1, ...)
{
  type_datum_t * type;
  uint32_t type_id;
  /* 1. 先查 p_types 符号哈希表：如果已经打过补丁存在该类型，直接复用其 type_id */
  type = hashtab_search (db->p_types.table, (hashtab_key_t) type_name);
  if (type == NULL)
  {
    type = malloc (sizeof (type_datum_t));
    type_datum_init (type);
    type_id = ++db->p_types.nprim; /* 分配新的递增 type_id (1-based) */
    type->s.value = type_id;
    type->primary = 1;
    type->flavor = TYPE_TYPE;

    /* 2. 将新类型插入 p_types 符号表并重建 sym_val_to_name 索引 */
    hashtab_insert (db->p_types.table, (hashtab_key_t) strdup (type_name), type);
    policydb_index_decls (NULL, db);
    policydb_index_others (NULL, db, FALSE);

    /* 3. 扩容 type_attr_map 与 attr_type_map 二维位图数组，并把新类型自身置位 */
    db->type_attr_map = realloc (db->type_attr_map, db->p_types.nprim * sizeof (ebitmap_t));
    db->attr_type_map = realloc (db->attr_type_map, db->p_types.nprim * sizeof (ebitmap_t));
    ebitmap_init (&db->type_attr_map[type_id - 1]);
    ebitmap_init (&db->attr_type_map[type_id - 1]);
    ebitmap_set_bit (&db->type_attr_map[type_id - 1], type_id - 1, 1);
  }
  else
  {
    type_id = type->s.value;
  }

  /* 4. 遍历可变参数列表 ("file_type", "mlstrustedobject")，双向绑定属性位图 */
  va_start (args, attr1);
  for (attr_name = attr1; attr_name != NULL; attr_name = va_arg (args, const gchar *))
  {
    type_datum_t * attr = hashtab_search (db->p_types.table, (hashtab_key_t) attr_name);
    uint32_t attr_id = attr->s.value;

    ebitmap_set_bit (&db->type_attr_map[type_id - 1], attr_id - 1, 1);
    ebitmap_set_bit (&db->attr_type_map[attr_id - 1], type_id - 1, 1);

    /* 5. 点睛之笔：同步修补所有 Class 里引用了该属性 (如 mlstrustedobject) 的编译期 Constraint 位图！ */
    if (!frida_add_type_to_class_constraints_referencing_attribute (db, type_id, attr_id, error))
      goto failure;
  }
  va_end (args);
  return TRUE;
}

static gboolean
frida_add_type_to_class_constraints_referencing_attribute (policydb_t * db, uint32_t type_id, uint32_t attribute_id, GError ** error)
{
  uint32_t class_index;
  for (class_index = 0; class_index != db->p_classes.nprim; class_index++)
  {
    class_datum_t * klass = db->class_val_to_struct[class_index];
    constraint_node_t * node;
    for (node = klass->constraints; node != NULL; node = node->next)
    {
      constraint_expr_t * expr;
      for (expr = node->expr; expr != NULL; expr = expr->next)
      {
        if (expr->expr_type == CEXPR_NAMES && ebitmap_get_bit (&expr->type_names->types, attribute_id - 1))
        {
          ebitmap_set_bit (&expr->names, type_id - 1, 1);
        }
      }
    }
  }
  return TRUE;
}

4.3 动态解析 $self 与改写 te_avtab 哈希表：frida_ensure_rule()（patch.c:342-424）

接下来，主循环遍历 frida_selinux_rules[13]。在进入循环前（L99-145），代码先判断规则中的 source 或 target 是否以 ? 开头：如果是可选类型且当前内核不存在该类型，直接跳过整条规则（if (is_important) return FALSE; else continue;）。

对于每一条有效规则，调用 frida_ensure_rule() 完成三件事：

  1. 动态解析 $self（L359-374）：如果 target 是 "$self"，调用 getcon (&self_context) 获取 frida-server 进程当前的 SELinux 上下文（例如 "u:r:su:s0" 或 Magisk 下的 "u:r:magisk:s0"），按冒号 ":" 分割取下标 tokens[2]（即 "su" 或 "magisk"）作为真实的 target 类型名！
  2. 双表查找权限位（L393-401）：在 SELinux 中，有些权限定义在类本身（如 file 类的 execute），而许多通用权限（如 read、write、open、getattr）定义在公共权限表 klass->comdatum->permissions.table 中。Frida 先查类自身表，查不到再查 comdatum 公共表，拿到权限编号后计算出位掩码 perm_bit = 1U << (perm->s.value - 1)。
  3. 在 db->te_avtab 哈希表中插入或按位或（L403-422）：构造四元组查询键 avtab_key_t key = { source->s.value, target->s.value, klass->s.value, AVTAB_ALLOWED }。如果哈希表里还没有这条边，就调用 avtab_insert() 新建一条；最后执行一句 av->data |= perm_bit; 将权限位打开！

static gboolean
frida_ensure_rule (policydb_t * db, const FridaSelinuxRule * rule, type_datum_t * source, type_datum_t * target, GError ** error)
{
  gchar * self_context = NULL;
  gchar ** tokens = NULL;

  /* 1. 如果 target 是 "$self"，通过 getcon() 动态提取 frida-server 当前所在的 SELinux type */
  if (target == NULL && strcmp (rule->target, "$self") == 0)
  {
    if (getcon (&self_context) != 0)
      goto failure;

    tokens = g_strsplit (self_context, ":", 4); /* 例如 "u:r:su:s0" -> tokens[2] == "su" */
    target = hashtab_search (db->p_types.table, tokens[2]);
  }

  class_datum_t * klass = hashtab_search (db->p_classes.table, (hashtab_key_t) rule->klass);

  for (perm_cursor = rule->permissions; *perm_cursor != NULL; perm_cursor++)
  {
    const gchar * perm_name = *perm_cursor;
    gboolean is_important = TRUE;
    if (perm_name[0] == '?') { is_important = FALSE; perm_name++; }

    /* 2. 先查 Class 专属权限表，若无则查 comdatum (Common Permissions) 公共权限表 */
    perm_datum_t * perm = hashtab_search (klass->permissions.table, (hashtab_key_t) perm_name);
    if (perm == NULL && klass->comdatum != NULL)
      perm = hashtab_search (klass->comdatum->permissions.table, (hashtab_key_t) perm_name);
    if (perm == NULL && !is_important)
      continue; /* 如旧内核无 ?map 权限，静默跳过 */

    uint32_t perm_bit = 1U << (perm->s.value - 1);
    avtab_key_t key = {
      .source_type = source->s.value,
      .target_type = target->s.value,
      .target_class = klass->s.value,
      .specified = AVTAB_ALLOWED,
    };

    avtab_datum_t * av = avtab_search (&db->te_avtab, &key);
    if (av == NULL)
    {
      avtab_datum_t new_av = { .data = 0 };
      avtab_insert (&db->te_avtab, &key, &new_av);
      av = avtab_search (&db->te_avtab, &key);
    }
    av->data |= perm_bit; /* 按位或打开权限位 */
  }
  return TRUE;
}

4.4 序列化写回 /sys/fs/selinux/load 与模拟器 shell 域兜底（patch.c:147-168, 203-213, 429-466）

当内存中所有的类型、MLS 位图和 13 条规则都修改完毕后，frida_save_policy() 调用 policydb_to_image(NULL, db, &data, &size) 把内存结构体重新打包成内核格式的二进制字节流，并通过自实现的 frida_set_file_contents("/sys/fs/selinux/load", data, size) 一次性写入内核。

这里有两个非常讲究的工程细节：

  • 为什么不用 GLib 的 g_file_set_contents()？（L429-466）：因为标准库的 g_file_set_contents() 为了原子性，会先在同目录创建临时文件 /sys/fs/selinux/load.XXXXXX 再 rename。但 /sys/fs/selinux 是内核虚拟文件系统 selinuxfs，根本不允许创建临时文件！所以 Frida 专门写了 frida_set_file_contents()，直接 open("/sys/fs/selinux/load", O_RDWR) 并循环 write()。
  • 模拟器 u:r:shell:s0 权限受限时的毫秒级闪切兜底（L148-168）：在部分官方 Android 模拟器上，Root 进程可能运行在受限的 u:r:shell:s0 域下，而默认策略不允许 shell 域直接向 /sys/fs/selinux/load 写入新策略，却允许它调用 security_setenforce(0)！于是 Frida 做了一个极其聪明的 Fallback：如果第一次写 /sys/fs/selinux/load 失败，且当前正在 Enforcing 模式，它会短暂执行 security_setenforce(0) → 在内存中把 shell 域加入 db.permissive_map（frida_ensure_permissive(&db, "shell")）→ 重新把策略写进 /sys/fs/selinux/load → 立即调用 security_setenforce(1) 恢复 Enforcing！

{

  size_t size;

为什么 Frida 不多不少刚好注入这 13 条 SELinux 规则？每一条规则分别对应注入流程里的哪一个系统调用？如果删掉其中某一条，注入会在哪一步崩溃？点击下方分类按钮可快速筛选：

序号 分类 SELinux 规则 (patch.c:41-53) 对应的注入阶段与大白话解释（删掉它会发生什么？）
#01
L41		 内存与代码映射 allow domain domain : process { execmem }; 允许所有进程分配并执行匿名 RWX 内存。
对应三处：① Stage 1 ptrace 在目标进程 mmap(PROT_READ|PROT_WRITE|PROT_EXEC) 放 bootstrapper.bin 和 loader.bin；② frida-gum 进行 Inline Hook（Interceptor）时动态生成的指令跳板（Trampoline）；③ V8 / QuickJS JIT 编译。若无此条，mmap(RWX) 或 mprotect(RX) 会直接报 EACCES。
#02
L42		 内存与代码映射 allow domain frida_file : dir { search }; 允许目标进程穿越标签为 frida_file 的临时目录。
当设备内核老于 Linux 3.17 不支持 memfd_create（或进入降级磁盘模式）时，frida-server 会在临时目录下释放文件并调用 adjust_directory_permissions() 打上 frida_file 标签。目标 App 必须有 dir { search } 才能解析该目录下的文件路径。
#03
L43		 内存与代码映射 allow domain frida_file : file { open read getattr execute ?map }; 允许目标进程加载并执行磁盘降级模式下的 frida-agent.so。
dlopen() 一个磁盘上的 .so 文件需要 sequentially 执行 open、fstat(getattr)、read（读 ELF 头）以及 mmap(PROT_EXEC)（触发 execute 和 Android 8+ 新增的 ?map 权限）。
#04
L44		 内存与代码映射 allow domain frida_memfd : file { open read write getattr execute ?map }; 允许目标进程通过 /proc/self/fd/N 映射并执行无文件内存中的 frida-agent.so（现代 Android 主路径）。
Stage 2 的 loader.bin 收到 SCM_RIGHTS 传来的 memfd 后，拼出路径 /proc/self/fd/%d 传给 dlopen()。内核在 do_filp_open 和 mmap_region 时会检查目标进程对 u:object_r:frida_memfd:s0 是否有 open/read/getattr/execute/map 权限。
#05
L45		 内存与代码映射 allow domain shell_data_file : dir { search }; 允许目标进程穿越 /data/local/tmp 目录。
在 Android 系统中，/data/local/tmp 的默认 SELinux 标签就是 u:object_r:shell_data_file:s0。普通 untrusted_app 默认被禁止 search 这个目录；如果不加这条，即使把里面的子目录或 .so 改成 frida_file，App 在解析路径第一层 /data/local/tmp/... 时就会被内核挡回。

#07

攻防视角：保持 Enforcing=1 就彻底无痕了吗？

既然 Frida 的 SELinux 热补丁如此精妙——既不改 /sys/fs/selinux/enforce，也不在磁盘上留下任何临时策略文件——那么站在高级反外挂 / RASP（运行时应用自我保护）风控团队的视角，还能不能检测出内核 SELinux 策略被 Frida 热修改过？如果自己魔改定制隐匿版 Frida，应该改哪里？

🛡️ 蓝军（风控检测方）vs 红军（定制魔改方）核心交锋点
实战对抗总结
风控方如何抓出 patch.c 的痕迹？ 3 种检测维度
  1. 直接试探 execmem 权限（普通 App 即可执行）：
    在标准 Android ROM 的 SELinux 策略下，如果 App 的 targetSdkVersion >= 29（Android 10+），untrusted_app 默认是没有 process { execmem } 权限的（尝试 mmap(NULL, 4096, PROT_READ|PROT_WRITE|PROT_EXEC, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) 会被 SELinux 拦截返回 EACCES）。但只要 frida-server 启动并打过补丁，因为第 1 条规则是 allow domain domain:process { execmem }（把所有进程都放开了！），普通 App 突然发现自己居然能成功申请匿名 RWX 内存了！
  2. 读取 /sys/fs/selinux/policy 检索特征字符串：
    在未封锁 selinuxfs 读取的机身或特权辅助服务下，直接扫描导出策略中的符号表，查找是否存在硬编码字符串 frida_file 或 frida_memfd。
  3. 观测 /proc/self/maps 或 /proc/self/fd 的 SELinux Context：
    对进程已映射的匿名内存 fd 调用 fgetfilecon() / getxattr(..., "security.selinux")，一旦读出 u:object_r:frida_memfd:s0 即可一锤定音。
深度定制/魔改 Frida 时如何抹除这些指纹？ 源码级去特征方案
  1. 重命名或复用系统既有合法 Type（消掉 frida_file / frida_memfd）：
    在 lib/selinux/patch.c:42-44, 85, 92 和 src/linux/linjector.vala:269, 276, 281 中，不要使用显眼的 "frida_file" 和 "frida_memfd"。可以改用随机生成的系统风格名称，或者直接复用系统中已自带 file_type 与 mlstrustedobject 属性的既有合法类型。
  2. 将 domain 收敛为按需针对性放行（修复 execmem 泛化漏洞）：
    官方 Frida 为了省事，在 frida_selinux_rules[] 里把 Source 全部写成了 "domain"（导致没被注入的检测 App 也能通过试探 mmap(RWX) 发现异常）。在定制版中，可以只对需要注入的目标域（或注入前按需打孔、甚至利用系统已具备权限的跳板）开放权限。
  3. 注入完成后卸载或还原规则：
    由于 /sys/fs/selinux/load 支持随时热更新，可以在修改前先把原始的 /sys/fs/selinux/policy 二进制流备份在内存中，待 Stage 2 dlopen(memfd) 完成且通信建立后，视业务需要裁剪不再需要的加载期规则。
